# Границы продукта Antidetect v2

> Статус: принятая продуктовая цель; реализация не подтверждена<br>
> Последняя ревизия: 2026-09-13<br>
> Авторитетен для: назначения продукта, MVP и non-goals
> Не авторитетен для: текущего состояния, схемы БД и деталей реализации

## Позиционирование

Antidetect v2 — Windows-first, local-first orchestrator браузерных профилей на Node.js/TypeScript.

ShardX предоставляет сторонний patched Chromium и fingerprint runtime. Наш проект создаёт control plane вокруг него:

- profile и proxy management;
- надёжный browser lifecycle;
- concurrency control;
- crash recovery и reconciliation;
- безопасную работу с credentials;
- диагностику и run history;
- локальные API и web UI;
- deterministic failure testing.

Проект не должен представлять ShardX engine или его fingerprint implementation как нашу разработку.

Исходный код нашего control plane может использоваться как публичная портфельная демонстрация, но текущая эксплуатация проекта остаётся личной и некоммерческой. Публикация нашего кода не включает бинарный ShardX engine, его архивы или производные файлы.

## Целевой пользователь

MVP предназначен одному локальному техническому пользователю, которому нужно:

- создавать и поддерживать изолированные browser profiles;
- назначать и проверять proxy;
- запускать профили в видимом окне для ручной работы; управление браузером внешними скриптами откладывается за пределы MVP;
- безопасно останавливать их;
- видеть фактическое состояние browser processes;
- разбирать lifecycle и engine failures.

Основная платформа первого релиза — Windows x64.

## MVP

В MVP входят:

1. Состояние ShardX engine и контролируемая первая установка.
2. Создание profile из поддерживаемой ShardX identity/template с выбором целевой платформы отпечатка (Windows, macOS или Linux); значение по умолчанию — Windows.
3. Список, rename, notes и безопасное удаление profile.
4. Создание, проверка, привязка и redacted display proxy.
5. Видимый запуск профиля для ручной работы; управление браузером внешними скриптами — вне MVP, возможное будущее расширение.
6. Безопасный и идемпотентный stop.
7. Защита от concurrent double-start.
8. Обработка unexpected browser exit.
9. Startup reconciliation после рестарта API.
10. Обнаружение stale и потерянного process state.
11. История browser runs и failures.
12. Live UI updates с восстановлением через обычный API read.
13. Законченный локальный web UI.
14. OpenAPI и stable machine-readable errors.
15. Unit, integration, concurrency и failure tests.
16. Настоящий Windows ShardX smoke test.
17. CI, setup, attribution, limitations и повторяемый demo flow.

### Fingerprint в профиле

По целевому контракту при создании по умолчанию автоматически назначается и
сохраняется поддерживаемый отпечаток браузера. Пользователь может сразу выбрать
допустимый режим «Без отпечатка». Отключение отпечатка не удаляет
последнюю назначенную идентичность профиля; повторное включение использует её же.
Замена назначает новую неизменяемую идентичность, а не изменяет старую.
Переключение режима, платформы и идентичности разрешено только между запусками,
когда профиль не занят. Отсутствие прокси означает прямое соединение (`Direct`),
а не необходимость настройки.

При создании профиля пользователь выбирает целевую платформу отпечатка из
поддерживаемых SDK вариантов: Windows, macOS или Linux. Это платформа браузерной
идентичности, а не операционная система компьютера-хоста; значение по умолчанию
остаётся Windows. Платформа сохраняется как настройка профиля и используется при
замене отпечатка или смене платформы. Сгенерированная конфигурация должна соответствовать выбору;
если SDK не может выдать такой вариант, профиль не сохраняется. Редактор отдельных
полей отпечатка в MVP не входит.

Этот выбор относится к настройкам профиля, а не к состоянию жизненного цикла:
режим «Без отпечатка» не означает `Setup required` («Требуется настройка»).
В обычной композиции API создание профиля с `fingerprintEnabled: true` вызывает
`ShardXFingerprintGenerator`: он получает шаблон из локальной библиотеки SDK,
создаёт новую неизменяемую идентичность и передаёт конфигурацию вместе с профилем
на сохранение одной транзакцией SQLite. Если генерация не удалась, профиль не
сохраняется. При `fingerprintEnabled: false` генератор не вызывается, а
`identityRef` равен `null`.

Если режим отпечатка включают позже у профиля без `identityRef`, сервис
жизненного цикла получает новую конфигурацию тем же генератором до начала
транзакции. Затем конфигурация и включённый режим сохраняются вместе в одной
транзакции SQLite. Ошибка генерации не меняет профиль; API возвращает безопасный
503 при недоступности локальной среды. Если identity уже сохранена, повторное
включение использует её без повторной генерации. Операция запрещена при активном
запуске и выполняется под блокировкой профиля.

Отдельная команда `POST /profiles/:profileId/fingerprint/replace` генерирует новую
идентичность и атомарно переключает профиль на неё. Текущий режим отпечатка не
меняется, старая запись идентичности не изменяется и не удаляется. Команда
выполняется под той же блокировкой профиля и отклоняется при активном запуске;
ошибка генерации оставляет профиль без изменений. В текущем срезе маршрут
доступен только в тестовой композиции с lifecycle-сервисом и не подключён к
обычному `main.ts`.

Платформу существующего профиля меняет `PATCH /profiles/:profileId/fingerprint/platform`
со строгим телом `{ fingerprintPlatform }`. Для включённого отпечатка сервис
генерирует новую соответствующую identity, затем одной транзакцией сохраняет её
и выбранную платформу; прежняя identity остаётся неизменной и не удаляется.
Для выключенного отпечатка генерация не запускается: новая платформа сохраняется,
`identityRef` очищается, а прежняя запись остаётся в хранилище. При последующем
включении создаётся identity уже для выбранной платформы. Повторный выбор текущей
платформы ничего не меняет. Операция выполняется под блокировкой профиля и
отклоняется при активном запуске; при ошибке генерации включённый профиль не
меняется. Селектор существует только в режиме `?fake-runtime`, поскольку маршрут
доступен только в композиции с lifecycle-сервисом, а не через обычный `main.ts`.

Генератор создаётся с `autoInstall: false`: запрос создания профиля не
устанавливает и не запускает браузер. При этом SDK требует полную локальную
установку ShardX, включая исполняемый файл, Widevine и библиотеку отпечатков;
если она отсутствует или неполна, API возвращает `503 FINGERPRINT_RUNTIME_NOT_READY`.
Режим без отпечатка от этой зависимости свободен. Успешная генерация и
сохранение конфигурации не подтверждают, что настоящий ShardX сможет запустить
её без ошибок; проверка совместимости при реальном запуске остаётся отдельными
воротами.

Генерацию при создании не следует смешивать с проверками жизненного цикла через
`FakeBrowserRuntime`, тестовую замену браузера: такие тесты не запускают
настоящий браузер. Контракт создания и его последствия описаны в ADR-0017.

## Не входит в MVP

- Bablosoft как поддерживаемый v2 runtime;
- несколько выбираемых browser engines;
- обычный Chromium как пользовательский antidetect runtime;
- cloud sync и multi-user registration;
- CAPTCHA solving и массовые multi-account flows;
- bulk start/stop;
- raw fingerprint editor;
- cookie import/export;
- folders, tags и pinning;
- MCP;
- Tauri, Electron или полноценный installer;
- uncontrolled automatic engine updates;
- перенос legacy fingerprints или sessions без отдельного исследования;
- Redis, BullMQ, Kafka, RabbitMQ или microservices;
- Kubernetes;
- observability stack только ради портфолио.

Эти функции требуют отдельного продуктового решения и не могут появляться в MVP неявно.

## Критерий продукта

MVP считается убедительным, если он доказывает, что:

- один profile нельзя случайно запустить дважды;
- потеря управления живым браузером не разрешает новый запуск или удаление профиля; занятость снимается только после подтверждения завершения принадлежащих запуску процессов либо отказа до их создания, согласно [ADR-0009](adr/0009-durable-profile-occupancy.md);
- database state не подменяет фактический process state;
- restart/crash behavior явно определено и проверяемо;
- stop воздействует только на правильный browser process tree;
- configured proxy failure не раскрывает host IP;
- credentials не попадают в обычные API, events, logs и diagnostics;
- UI восстанавливает актуальное состояние после reconnect;
- failure scenarios воспроизводятся без обязательного реального browser;
- новый разработчик понимает границу ShardX и нашего кода.

Подробные acceptance scenarios находятся в `docs/development-plan.md`.

## Лицензионная граница

ShardX — сторонний closed-source engine с отдельными условиями. Проект обязан:

- загружать engine только поддерживаемым официальным способом;
- не commit, mirror, bundle или redistribute его binary;
- явно указывать attribution;
- отличать лицензию нашего исходного кода от engine terms;
- использовать engine только локально для личного некоммерческого проекта, как явно подтвердил пользователь 20 августа 2026 года;
- сохранять актуальные публичные условия и повторно проверять их перед существенным обновлением;
- остановить коммерциализацию, публичный сервис или распространение движка до отдельного письменного разрешения ProxyShard.

## Открытые продуктовые решения

После закрытия практического Phase 0 и до реализации соответствующих слоёв или отдельного threat-model review — разбора модели угроз — остаются открытыми:

- recovery policy, если к живому process нельзя reattach;
- возможная защита от произвольных программ на самом компьютере; она не входит в принятую границу угроз MVP и потребует отдельного пересмотра scope;
- хранение proxy credentials на Windows;
- sync/async HTTP semantics browser launch;
- integrity и update policy ShardX components.

Принятое целевое решение MVP от 30.09.2026: только видимый ручной режим; ShardX запускается с `cdp: true` исключительно для внутренних команд остановки и восстановления адаптера. Внешняя автоматизация не входит в рамки MVP. Адрес CDP (`Chrome DevTools Protocol` — протокол управления Chromium) нельзя выдавать через API, события, журналы или диагностику; он должен оставаться на loopback (локальном сетевом интерфейсе). Это решение, а не реализованная гарантия: безопасное обнаружение адреса после перезапуска API, проверка идентичности процесса и подтверждение его выхода остаются воротами D-001/D-005/D-006. Остаточный риск `--remote-allow-origins=*` из проверенного SDK принят для ограниченного однопользовательского MVP без сетевой экспозиции.

Они зарегистрированы в `docs/risk-and-decision-log.md` и не являются реализованными гарантиями.

## Правило изменения scope

Изменение MVP, поддерживаемого runtime, security model, persistence model, public API или deployment model требует явного решения до реализации.

При нехватке времени сначала сокращаются декоративный UI и вторичные функции. Lifecycle correctness, recovery, credential safety и failure tests остаются обязательными.
