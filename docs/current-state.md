React/Vite web skeleton по умолчанию запрашивает `/api/profiles` через локальный Vite proxy и валидирует ответ тем же контрактом; форма `Create profile` отправляет `displayName` и `fingerprintEnabled` (по умолчанию `true`), показывает `isSubmitting`/безопасную ошибку и после успешного ответа перечитывает список с сервера. Сервер создаёт тестовую identity только при включённом отпечатке и сохраняет выбранный режим в SQLite; при создании без отпечатка `identityRef` равен `null`. `?demo` оставлен для визуальной проверки статических demo profiles — демонстрационных профилей — и является read-only режимом. Server-backed список показывает loading/error/empty states, поиск/фильтр/сортировка остаются локальными до расширения API-среза, а отсутствующие status/proxy поля отображаются явными нейтральными placeholders — временными значениями представления — без утверждения о готовности профиля; для lifecycle-поля UI использует `Unknown`, а не `Ready` или `Setup required`. Команда `BrowserLifecycleService.updateFingerprintMode` переключает режим только у свободного профиля: отключение сохраняет `identityRef`, повторное включение переиспользует его, а при `null` создаёт тестовую ссылку. В тестовой API-композиции с `FakeBrowserRuntime` для неё доступен защищённый сессионной cookie маршрут `PATCH /profiles/:profileId/fingerprint`; в интерфейсе `?fake-runtime` переключатель отправляет эту команду, отображает новое значение только после успешного ответа и показывает конфликт занятого профиля. Ни маршрут, ни переключатель не подключены к обычному `main` и не запускают браузер; реальное создание и применение отпечатка через ShardX не реализованы и не проверены.

- В Phase 3 добавлен проверяемый API composition slice: `BrowserRunsModule` принимает готовый `BrowserLifecycleService`, а тестовая сборка `buildApp()` подключает `POST /profiles/:profileId/start`, `POST /profiles/:profileId/stop` и `GET /profiles/:profileId/run` с `FakeBrowserRuntime`. По ADR-0015 Start/Stop возвращают `202` после сохранения `starting`/`stopping`, не дожидаясь движка; Stop во время `starting` быстро получает `409`, повторный Stop при `stopping` не создаёт второй вызов, а GET возвращает последний запуск, включая конечный статус. Ограниченное ожидание и поздние ответы сохраняют занятость до подтверждения исхода. Контракт отдаёт только run state, не публикует PID/process identity. Тесты сервиса жизненного цикла дополнительно проверяют, что после пересоздания среды выполнения сервис повторно подключается к процессу только при совпадении `runId`/`profileId` (идентификаторов запуска и профиля), PID (идентификатора процесса) и `processIdentity` (проверяемой идентичности процесса), восстанавливает подписку на завершение и продолжает наблюдение. При точном совпадении и успешном переподключении запись `recovery_required` возвращается в `running` с очищенным `failureCode`; неизвестная идентичность, таймаут или ошибка поиска оставляют профиль занятым в `recovery_required`, а подтверждённый выход процесса переводит запуск в `failed`. Это тестовая политика, а не поиск процессов средствами ОС. Обычный `main` пока не подключает тестовую подмену; реальная среда выполнения, подключение восстановления при старте API, завершение и усиленная граница доступа остаются открытыми.

Это проверка логики на `FakeBrowserRuntime`, а не наблюдение за настоящим процессом ОС; обычный `main` пока не запускает этот recovery автоматически.

Схемы, application service, API, SQL pagination/filter/sort, OpenAPI, HTTP-проверки и UI-сценарий создания реализованы в текущей рабочей ветке; более сильная local authentication остаётся обязательной границей перед секретами и управлением браузером.
- Следующие технические шаги: process-aware recovery и shutdown policy в Phase 3; базовый session gate остаётся. UI-команды проверяются только через отдельный fake-режим; ordinary runtime wiring отсутствует. CSRF/custom-header policy для state-changing чувствительных маршрутов и удалённый CI требуют отдельных проверок.

### Startup и application directories

`apps/api/src/main.ts` является composition root — местом связывания конфигурации и инфраструктуры. После проверки `API_PORT` он вызывает `resolveAppPaths()`, создаёт только `rootDir` и `dataDir`, получает `acquireRootOwnership()`, проверяет базу и выполняет миграции, затем создаёт остальные каталоги, выполняет `buildApp()` и `app.listen()`. Занятый run не является глобальным отказом старта и сохраняется в SQLite; startup integration test проверяет `/health=200` при `recovery_required`, а также отказ второго владельца до порта, продолжение работы владельца и повторный захват после его завершения.

При указании файла вместо корня `ensureAppRootDirectories()` завершает процесс с `ENOTDIR`, HTTP-порт не открывается, а исходный файл не заменяется. Это подтверждает fail-closed — остановку при небезопасной ошибке — на текущем startup-слое; Windows ACL, recovery и graceful shutdown остаются отдельными задачами.

ADR-0010 фиксирует и частично реализует порядок запуска: до миграций, продуктовых каталогов и открытия HTTP основное SQLite-соединение получает эксклюзивную блокировку корня и удерживает её до завершения API без длительной транзакции. Базовый guard и локальная startup integration-проверка проходят; `ApiRuntime` освобождает root только после успешного закрытия HTTP-приложения, а при ошибке или таймауте закрытия сохраняет блокировку fail-closed и завершает процесс с ошибкой по bounded shutdown policy — политике ограниченного завершения. После смерти процесса ОС освобождает lock, но profile recovery, платформенное поведение сигналов и Linux CI ещё не приняты.

ADR-0011 фиксирует базовую request policy: API привязан только к literal loopback, а Fastify hook проверяет ровно один `Host` и допустимый same-origin `Origin`. ADR-0014 добавляет memory-only session cookie для текущих product routes. Это снижает риск запросов с вредоносной страницы, но не является OS authentication — проверкой личности локального процесса, — поэтому доступ к секретам, Start/Stop и CDP требует отдельного решения.

Внутри подтверждены Windows 10 Pro 22H2, сборка `19045.6456`, включённые Microsoft Defender и все профили межсетевого экрана. После этого `LanmanServer` и `vmicvmsession` — служба PowerShell Direct, прямого управления виртуалкой с основной системы — остановлены и отключены. Пользователь явно подтвердил, что после чистой установки не входил в личные аккаунты, не копировал личные файлы и не вводил пароли, ключи или данные прокси.

На основной Windows подтверждены сборка `26200.9168`, включённые антивирус, защита в реальном времени, поведенческий мониторинг и сетевая проверка угроз Microsoft Defender; сигнатуры обновлены 18 августа 2026 года, все три профиля межсетевого экрана включены. Перед созданием точки на `C:` было 126 ГБ свободно. При штатно выключенной `Win10` создана единственная исходная контрольная точка `pre-shardx-clean-baseline-2026-08-19` от 19 августа 2026 года, 23:16:48. Политика машины осталась `ProductionOnly`, а `Checkpoint-VM` завершилась успешно. `Get-VMSnapshot` сообщил `SnapshotType: Standard`; это поле использует другую классификацию без значения `Production` и не доказывает запасной переход к стандартной точке. Аудит 20 августа 2026 года без загрузки файлов подтвердил официальный пакет `@proxyshard/shardx@0.1.11`, его открытый Node SDK — комплект разработки — и публичные условия личного использования. Пользователь определил Antidetect v2 как личный некоммерческий проект без продажи, публичного сервиса и распространения движка. Это закрывает лицензионную неопределённость только для текущего scope — границы проекта — но не проверку цепочки поставки. После отдельного разрешения применён временный `WinNAT` `ShardX-Temp` для `192.168.250.0/24`. В гостевой Windows вручную настроены `192.168.250.10/24`, шлюз `192.168.250.1` и DNS `1.1.1.1`. Внутри гостевой Windows установлены Node.js `24.19.0` и pnpm `11.16.0`; PowerShell блокирует `npm.ps1`, поэтому для bootstrap — первичной установки — использовались `npm.cmd` и `pnpm.cmd` без ослабления execution policy — политики выполнения сценариев.

### Обновление эксперимента ShardX в виртуальной машине от 2026-08-20

Пользователь отдельно разрешил одноразовый эксперимент только внутри `Win10`. В `C:\ShardX-Spike` загружен архив `@proxyshard/shardx@0.1.11` размером 48 595 байт; его SHA-512 был преобразован в SRI — строку контроля целостности — и совпал с опубликованным значением (`True`). SDK установлен из этого локального архива через `pnpm.cmd add 'file:.\shardx-0.1.11.tgz' --ignore-scripts`; install-скрипты при этом не запускались.

Первый вызов `new ShardX().listProfiles()` получил runtime — среду выполнения — и библиотеку отпечатков; вывод содержал непустой список и был сокращён терминалом как `... 700 more items`. Затем создан тестовый сохранённый profile и выполнен headful launch — запуск браузера с видимым окном. Пользователь подтвердил открытие `about:version` и `https://example.com`.

Штатный lifecycle — жизненный цикл — наблюдался через `BrowserSession`: `s.pid` и `s.process.pid` были `5892`, `process` являлся `ChildProcess` — объектом дочернего процесса Node.js, а после закрытия окна пришло событие `exit 0 null`. Повторный запуск того же сохранённого profile использовал ту же папку данных; это подтверждает сохранение записи profile, но ещё не persistence — сохранение именно браузерных данных, например cookie. Второй одновременный `launch()` того же profile не был отклонён и вернул `SECOND_LAUNCHED 4716`; второй сеанс был остановлен командой теста. Это доказывает отсутствие гарантии SDK «один активный запуск на profile», но не доказывает отсутствие всех возможных файловых блокировок.

21.08.2026 практическое выполнение Phase 0 закрыто как ограниченный evidence-spike: дополнительно наблюдались CDP с/без listener, отсутствие воздействия CDP-close на вручную запущенный foreign Chromium и orphan tree из шести Chrome-процессов после намеренного завершения launcher спустя пять секунд running. Это устанавливает архитектурные требования, но не является принятием runtime для production.

Непроверенные interrupted/concurrent first install, integrity закрытых архивов, reused PID, automatic recovery, рабочий proxy/external IP/DNS/QUIC/WebRTC и fingerprint surfaces перенесены в обязательные phase gates. Цепочка поставки не принята; одноразовое разрешение не является общим разрешением на повторную загрузку, обновление или запуск ShardX. Подробный протокол: [phase-0-shardx.md](spikes/phase-0-shardx.md).

## История: что было реализовано в старом прототипе

- Prisma schema и начальная SQLite migration;
- базовые repositories;

## Что не реализовано в публичной V2

- интеграция `ShardXRuntime` в код v2; отдельный VM-spike частично выполнен, но не заменяет этот adapter — адаптер внешней среды выполнения;
- настоящий `BrowserRuntime` для браузера; application port и управляемый `FakeBrowserRuntime` уже реализованы для тестов;
- process-aware recovery — восстановление с проверкой процесса, PID/process identity, durable process registry и reconciliation; read-only recovery barrier уже реализован;
- crash/restart recovery;
- SSE и обновление UI через поток событий; отдельный fake-runtime UI/API-срез Start/Stop и чтение последнего запуска уже работают;
- решение по хранению proxy credentials;
- более сильная local authentication и CSRF/custom-header policy для чувствительных localhost API; базовая Host/Origin boundary и session cookie уже реализованы;
- обязательный Pino redaction;
- browser-level end-to-end test — сквозная проверка в настоящем браузере — для create/restart/read; API persistence и web API client проверены раздельно;
- component-level UI tests — тесты React-компонентов — и SSE; последний полный локальный набор содержит 207 тестов по contracts, API, persistence, security boundary и fake lifecycle;
- полный набор Windows ShardX smoke tests — кратких проверок среды выполнения; есть только ограниченное VM-evidence — доказательство из виртуальной машины;
- Реальное восстановление процессов ОС, ShardX runtime и подтверждённый удалённый CI остаются открыты. Browser-control module/routes работают только в отдельном fake API-срезе; `main.ts` не подключает runtime. Profile API/UI, persistence и локальные format/lint/typecheck/test/build проверки реализованы и проверены.

## История: расхождения старого прототипа с целевой V2

Следующие пункты объясняют отказ от прототипа по ADR-0005. Они не описывают код `antidetect-v2-public` и не являются списком текущих дефектов её реализации.

1. Runner старого прототипа использовал Bablosoft, а не ShardX.
2. Состояние запуска хранится через `Profile.isOpen` и in-memory `Map`; durable double-start protection и recovery отсутствуют.
3. `LifecycleService` передаёт proxy в `LaunchOptions`, но `Runner.launch()` его не применяет и использует `loadProxy: false`. Успешная проверка proxy не доказывает, что browser запущен через proxy.
4. Proxy password хранится в SQLite открытым текстом.
5. Profile path строится из имени, а rename перемещает каталог. В v2 path должен строиться из UUID и не меняться при rename.
6. Fingerprint меняется на месте, тогда как target v2 предполагает immutable ShardX identity.
7. Корневой `src/` дублирует `packages/*`.
8. Предыдущая target architecture предлагала PostgreSQL, Redis/BullMQ и worker, что противоречит принятой v2 baseline.
9. Старые ADR фиксировали Playwright/FingerprintSwitcher runner и не являются действующими решениями v2.
