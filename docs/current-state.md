## Изолированный вызов запуска ShardX — 2026-10-05

Добавлен `ShardXLaunchAdapter`, инфраструктурный компонент только для запуска. Он читает существующую запись `starting` через `BrowserRunRepository.findById`, сверяет запуск и профиль, фиксирует `createdAt` до дальнейших ожиданий и использует прежний `prepareStored`. Контракт `RuntimeLaunchInput` не изменён; адаптер не сохраняет состояния и не генерирует отпечатки. Отсутствующая или некорректная запись и ошибки подготовки дают фиксированный `failed_before_spawn`, отказ до создания процесса. Уже сохранённые метаданные процесса требуют восстановления. Дополнительный запрет перекрывающихся вызовов действует только для одного профиля внутри экземпляра адаптера и не заменяет прикладную блокировку или ограничение SQLite.

Перед вызовом SDK, библиотеки взаимодействия с ShardX, нужна полная проверка отсутствия процессов профиля. Неполная проверка или существующее дерево дают `spawn_uncertain`, неопределённость запуска, без вызова `launch` и перезаписи файлов работающего профиля. Подтверждено по коду и отдельной проверкой установленной библиотеки: SDK добавляет UUID профиля к параметру `userDataDir`. Поэтому адаптер передаёт в этот параметр `profilesDir`, корень каталогов профилей; подготовленный и проверяемый конечный каталог остаётся `profilesDir/<profileId>`, без двойного UUID. Параметры `randomize: false`, отсутствие повторной рандомизации, `headless: false`, видимый режим, и `cdp: true`, внутренний протокол управления Chromium, сохраняются. SDK может изменять рабочую конфигурацию при запуске; сохранённая идентичность от этого не переписывается, а фактический отпечаток движка ещё не проверен.

После ответа SDK повторно сверяются путь к исполняемому файлу, каталог, время создания, дерево, владелец локального порта CDP и совпадение PID, числового идентификатора процесса, с объектом дочернего процесса SDK. Только подтверждённый живой процесс возвращает `started`, успешный запуск, с нашим `RuntimeProcess`; адрес CDP, SDK-сессия и исходные ошибки в результат не попадают. Отказ SDK после возможного создания процесса, неполная проверка, несовпадение или ранний выход сохраняют неопределённость без автоматического повторного запуска или принудительного завершения.

Подписка на выход устанавливается до повторной проверки идентичности. Уже завершившийся объект SDK и завершение во время проверки не могут подтвердить более поздний процесс с переиспользованным PID. После выхода корня выполняется до трёх проверок отсутствия всего дерева, с промежутками 100 и 250 мс; сами проверки Windows ограничены прежним сроком источника. Уведомление о выходе разрешено только после полного `absent`, подтверждённого отсутствия. Неразрешённый результат не даёт такого уведомления и оставляет занятость для будущего восстановления; бесконечного опроса нет. Подтверждённый выход сохраняется для поздних подписчиков. Код `0` без доказательства штатной команды закрытия даёт `kind: unknown`, неизвестную причину; ненулевой код или сигнал — `abnormal`, аварийное завершение. Штатная остановка через CDP и единая классификация её результата с уведомлением — следующий отдельный шаг.

## Изолированная остановка ShardX — 2026-10-07

В `ShardXLaunchAdapter` добавлен метод `stop` — остановка процесса, запущенного тем же экземпляром адаптера. Перед закрытием он заново сверяет запуск с полным снимком процессов, проверяемой идентичностью корневого процесса и владельцем порта CDP (Chrome DevTools Protocol, протокол управления Chromium). Адрес берётся только из полученной SDK-сессии; он проверяется на локальный IP-адрес и точное совпадение порта, остаётся внутри адаптера и не попадает в `RuntimeProcess`, API, журналы или сохранённые данные.

Для закрытия используется команда `Browser.close` через `WebSocket` — двустороннее соединение с loopback, локальным сетевым интерфейсом. Адаптер требует подтверждение именно этой команды, затем ограниченно повторяет проверку дерева процессов с растущими интервалами. Только полный снимок `absent` — подтверждённого отсутствия процессов — завершает остановку; классификация причины совпадает с уведомлением `onExit`. После подтверждённого `Browser.close` отсутствие ненулевого кода или сигнала даёт `normal` — штатное закрытие; код `0` без подтверждённой команды остаётся `unknown` — причина неизвестна. Неизвестная проверка или превышение срока даёт таймаут, а профиль остаётся занят для восстановления. Принудительная остановка процессов не вызывается.

Метод `BrowserSession.stop()` SDK не используется: его установленная реализация отправляет SIGTERM — запрос завершить процесс, — а затем может перейти к SIGKILL — принудительному завершению. Команда CDP отправляется только после проверки того, что локальный порт принадлежит подтверждённому дереву нужного профиля. Положительный протокольный тест использует подменный `WebSocket`; реальное соединение с браузером не открывалось.

Добавлено 7 тестов остановки; всего адаптер покрыт 42 тестами. Они проверяют подтверждение `Browser.close`, повторный Stop без второй команды, владельца порта, недопустимый адрес, ошибочный ответ, оставшиеся процессы, таймаут и отсутствие вызова `ChildProcess.kill`. Прошли `corepack pnpm test` (41 файл / 528 тестов), `corepack pnpm run typecheck`, `corepack pnpm run lint`, `corepack pnpm run format:check` и `corepack pnpm run build`. `test:integration` не запускалась: обычная точка входа не менялась.

Это всё ещё изолированный фрагмент запуска и остановки, не полный `BrowserRuntime`: восстановление через CDP после перезапуска API не реализовано, обычный `main.ts` его не использует. Настоящий ShardX и Windows-процесс не проверялись; D-001/D-006/D-008 остаются открытыми. Движок не скачивался и не устанавливался, браузер не запускался; коммита и отправки нет.

## Повторная попытка Stop — 2026-10-08

Одновременные вызовы `stop` используют одну внутреннюю попытку. После успешной остановки результат сохраняется для идемпотентных повторов. Завершившийся отказ освобождает попытку; следующий вызов сначала заново проверяет идентичность дерева процессов и владельца CDP, и лишь затем снова отправляет `Browser.close`. Неверный таймаут не сохраняется как результат попытки.

Если срок ожидания вызывающего кода истёк, пока внутренняя остановка ещё не завершилась, повторный вызов продолжает получать тот же неопределённый результат: вторая команда закрытия не отправляется. После фактического завершения неуспешной попытки можно начать новую проверку. Позднее подтверждённое отсутствие процесса имеет приоритет над сохранённым таймаутом и возвращается как `stopped`.

Три новые регрессионные проверки подтверждают повтор после отказа CDP с новой проверкой идентичности, отсутствие кеширования неверного таймаута и обработку подтверждённого позднего выхода после таймаута. Адаптер теперь покрыт 45 тестами; целевой файл прошёл 45/45. Это синтетические проверки без ShardX, браузера и сетевых обращений; обычный `main.ts` по-прежнему не подключает адаптер.

## Подготовка запуска из сохранённого отпечатка — 2026-10-05

В `ShardXLaunchPreparer` добавлен `prepareStored`: он принимает прежний `RuntimeLaunchInput` и только метод чтения `FingerprintIdentityRepository.findById`. До чтения проверяются UUID профиля и запуска, точный ожидаемый каталог, режим отпечатка и UUID ссылки. Входные поля фиксируются до первого ожидания. Прежний `prepare` сохранён; общие проверки входа используют один внутренний метод.

После чтения должны совпасть UUID идентичности и поддерживаемая версия `1`; затем конфигурация передаётся прежней подготовке отдельной рабочей копией с `randomize: false`. Нет записи, повреждённые данные, неподдерживаемый формат или ошибка чтения дают фиксированный `failed_before_spawn / RUNTIME_FINGERPRINT_UNAVAILABLE`, отказ до создания процесса, без исходных подробностей и без обращения к SDK, библиотеке ShardX. ## Прикладное создание профиля с отпечатком — 2026-10-05

## Локальный статус файлов движка — 2026-10-03

Добавлены `GET /engine/status` и компактная плашка ShardX внизу боковой панели с ручным обновлением. Источник — только `runtimeDir`, каталог среды выполнения текущего корня V2. Настоящий адаптер браузера и SDK (комплект разработки ShardX) для этой проверки не подключаются; сеть установщика, создание файлов, установка, обновление и запуск движка не вызываются. Отдельный тестовый запуск API также читает реальный локальный каталог, а не сообщает вымышленную установку.

Состояния: `not_installed` — каталог отсутствует или пуст; `files_detected` — обнаружены Windows-исполняемый файл с заголовком MZ, непустой Widevine, хотя бы один JSON-файл отпечатка и корректно записанная версия Chromium; `incomplete` — локальные файлы неполны или метаданные некорректны; `recovery_required` — присутствует отметка незавершённого обновления `.runtime-update-recovery`; `unavailable` — чтение невозможно либо платформа не Windows. Проверка не разбирает содержимое всех отпечатков и не подтверждает готовность SDK, совместимость, криптографическую целостность, принадлежность процесса или успешный запуск. Пути, исходные ошибки и прочие метаданные не выходят в ответ API. Версия берётся из локального `manifest.json`, а не из текущего сетевого манифеста. Неудачная проверка в интерфейсе убирает прежний статус; обновление ограничено пятью секундами и не запускает фоновый опрос.

Тестовый сервер не требует каталога данных ради необязательной диагностики движка: без `ANTIDETECT_HOME`/`LOCALAPPDATA` либо вне Windows маршрут возвращает `unavailable`, не мешая работе `FakeBrowserRuntime`. При заданном каталоге на Windows читает локальные файлы. Обычный запуск `main.ts` по-прежнему требует корректный корень приложения. Маска исключений ESLint, средства анализа кода, исправлена на `**/dist/**`, чтобы проверка исходников не зависела от наличия вложенных результатов сборки.

После исправлений аудита прошли `corepack pnpm test` (33 файла / 342 теста), `corepack pnpm run typecheck`, `corepack pnpm run test:integration` (сборка и 4/4 межпроцессных проверки), `corepack pnpm run lint` после сборки, `corepack pnpm run format:check` и `git diff --check`. Добавлен регрессионный тест импорта тестовой точки запуска без обеих переменных каталога. Отдельно запущен собранный тестовый сервер с удалёнными из окружения процесса `ANTIDETECT_HOME` и `LOCALAPPDATA`: `/health` и защищённый сессией `/engine/status` вернули HTTP 200, состояние движка — `unavailable`. Процесс проверки остановлен; фактический запуск на Linux отдельно не выполнялся.

Это локальная диагностика, не установщик и не закрытие D-008. Уже установленный движок в отдельной виртуальной машине не означает его наличие в корне V2 основной системы. Проверки используют синтетические файлы; настоящий движок не скачивался и не запускался.

## Подготовка и VM-проверка инвентаризации процессов — 2026-10-03

Добавлены чистая функция-классификатор (сверяет уже собранные данные, ничего не меняя в системе) `identifyShardXProcess` и сборщик сведений о процессах Windows только для чтения (read-only). Он читает метаданные `chrome.exe`, извлекает `user-data-dir` (путь к каталогу данных профиля), время создания, PID (идентификатор процесса) и родительский PID, а при наличии `DevToolsActivePort` (файла с портом CDP, протокола управления браузером) сверяет локальный TCP-listener (порт, принимающий соединения). Исходные командные строки не включаются в результат. Неразобранные процессы, неполные данные и ошибки остаются неоднозначностью; источник не объявляет, что процесс-запускатель отсутствует (`pendingLauncher: none`), сам — это обязан подтвердить адаптер.

Это только изолированные инфраструктурные компоненты: `BrowserRuntime.recover` и обычный `main.ts` ими не пользуются. 03.10.2026 пользователь выполнил зонд на PowerShell (оболочке команд Windows) в одноразовой VM с уже имевшейся средой выполнения ShardX; её повторно не скачивали и не устанавливали. До запуска и после штатного закрытия зонд не обнаружил `chrome.exe` и процессов с каталогом профиля SDK (комплекта разработки) (`NO_MATCHING_SHARDX_PROFILE_PROCESS`, код `2`). В активном снимке он нашёл семь `chrome.exe` ожидаемого пути ShardX, связанных с одним существующим профилем; владелец CDP-слушателя (локального порта протокола управления Chromium) входил в это дерево (`PASS_SHARDX_PROFILE_AND_CDP_OWNER_ASSOCIATION`, код `0`). Родительским процессом был `node.exe`, но поле `ParentIsSmokeLauncher` вернуло `False`, поэтому связь с конкретным процессом тестового запуска не доказана. Сырые командные строки и адрес CDP не выводились; сетевые запросы, команды браузеру и завершение процессов зондом не выполнялись. Проверка не подключает сборщик к `BrowserRuntime.recover` или `main.ts` и не доказывает восстановление `runId` (идентификатора запуска) после перезапуска API (программного интерфейса). D-001/D-006/D-008 остаются открытыми. Подробности: [результаты проверки в VM](spikes/phase-0-shardx.md).

Проверки текущего дерева: 29 файлов / 321 тест, typecheck, lint и Prettier для четырёх изменённых файлов прошли; `git diff --check` прошёл с прежними предупреждениями о CRLF в `docs/product-scope.md` и `docs/spikes/phase-0-shardx.md`. Сборка после этих изменений не запускалась.

## Финальное закрытие аудита Phase 3 — 2026-10-02

Проверена текущая локальная версия с ранее согласованными исправлениями. Аудит Phase 3 закрыт в принятой границе `FakeBrowserRuntime`, тестовой замены движка. Исправления не меняют схему БД (базы данных), зависимости или набор публичных маршрутов; результат остановки сохранённого `stopping` без выполняющейся задачи уточнён в ADR-0015.

Все правки аудита:

1. Подтверждённый выход имеет одну классификацию для события, ответа остановки, очистки и восстановления. Неизвестная причина уже доказанного завершения освобождает профиль с `failed`; неизвестное состояние процессов сохраняет занятость. Конечный результат и `endedAt` (время завершения) не переписываются поздним ответом.
2. Известная исходная ошибка запуска сохраняется отдельно от временных ошибок очистки; после успешного переподключения и сохранения `running` устаревший контекст снимается. После перезапуска службы восстановление исходной ошибки из памяти не заявляется.
3. Незавершённые операции учитываются по `runId` (идентификатору запуска), включая поздние результаты и продолжающийся поиск процесса. Пока такая операция выполняется, новый поиск и преждевременный возврат в `running` не разрешаются. Ошибка записи таймаута не теряет обработчик позднего результата.
4. Сохранённый `stopping` без текущей задачи переходит в `recovery_required` с `RUNTIME_STOP_INTERRUPTED` до проверки процесса. Подтверждённое переподключение возвращает управление и обновляет подписку на выход, без автоматического повторения остановки. Подтверждённое отсутствие процесса завершает запись и освобождает занятость.
5. Финальный проход воспроизвёл превышение срока закрытия API (программного интерфейса) при медленном восстановлении `starting`: проверка удерживала блокировку профиля. Теперь на дедлайне прерывается её ожидание и снимается таймер, после чего сохраняется занятость неразрешённых запусков. Сам вызов движка остаётся учтённым до завершения, его поздний результат не применяется. Новые проверки восстановления после начала закрытия не запускаются. Дополнительно исправлено преждевременное закрытие во время записи результата восстановления: учитывается полная обработка, а перед окончательным закрытием синхронизируются блокировки всех занимающих профиль запусков. Уже начатая запись обязательна; её задержка не выдаётся за успешное закрытие, внешний ограничитель `ApiRuntime` сохраняет владение корнем при превышении срока. Добавлены десять сценариев с управляемым ответом, задержанной записью и виртуальным таймером; служба проходит 104 теста.
6. Устранены противоречия активных документов: ADR-0009 теперь отражает реализованную сохраняемую занятость; общая блокировка готовности API заменена проверками конкретного профиля; D-002 принят для браузерных запросов по ADR-0016. Защита от произвольной локальной программы средствами ОС не входит в MVP. Исторические результаты проверок ниже сохранены как датированные снимки.

## Аудит Phase 3 — 2026-10-02, третий шаг исправлений

- Сохранённый `stopping` (остановка выполняется) больше не пропускается при восстановлении. Если текущая служба ещё учитывает задачу остановки, она продолжает выполняться без второго вызова. Если задачи нет, сначала сохраняется `recovery_required` с `RUNTIME_STOP_INTERRUPTED`, затем проверяются процессы. Повторная команда без задачи получает `409 BROWSER_RUNTIME_RECOVERY_REQUIRED`, а не бесконечный ответ `202`.
- Подтверждённое переподключение возвращает `running` без автоматического повторения остановки и обновляет подписку на выход. Старый контекст очистки снимается только после успешного сохранения `running`; неудачная проверка или запись сохраняют известную исходную ошибку запуска. Подтверждённое отсутствие процессов сохраняет эту исходную ошибку, если она ещё известна, и после записи конечного состояния снимает подписку и контекст.
- `corepack pnpm run format:check`, `corepack pnpm run lint`, `corepack pnpm run typecheck`, `corepack pnpm test` и `corepack pnpm run build` прошли: 27 файлов, 280 тестов, включая 25 новых сценариев этого шага. Четыре из них закрывают и повторно открывают настоящую временную SQLite-БД, проверяют сохранённый `stopping`, новые результаты проверки и ограничение занятости. Состояние процессов моделирует `FakeBrowserRuntime`, тестовая замена движка.
- На момент третьего шага оставались сверка активных документов с кодом и полный набор проверок закрытия фазы. Они выполнены при финальном закрытии выше. Обычный `main` не подключает ShardX; проверки настоящих процессов и условия Phase 4 остаются отдельными.

## Аудит Phase 3 — 2026-10-02, второй шаг исправлений

- Добавлен учёт незавершённых операций по `runId` (идентификатору запуска). Проверка восстановления не вызывается, пока продолжается запуск, остановка, очистка или предыдущая проверка того же запуска. Таймаут ожидания не снимает учёт; поздние ответы запуска и остановки сохраняют обработчик даже при ошибке записи таймаута в БД (базе данных). Другой профиль продолжает работать.
- Поздний результат истёкшей проверки восстановления не меняет сохранённую запись; после фактического завершения вызова допускается новая проверка. Реестр действует только в памяти текущей службы и не заменяет сохраняемую занятость SQLite или проверку процессов после перезапуска.
- `corepack pnpm run format:check`, `corepack pnpm run lint`, `corepack pnpm run typecheck`, `corepack pnpm test` и `corepack pnpm run build` прошли: 27 файлов, 255 тестов, включая 12 новых сценариев этого шага. ## Аудит Phase 3 — 2026-10-02, первый шаг исправлений

Страница предупреждает, что это симуляция без реального браузера. Обычный `main.ts`, SQLite и каталоги пользовательских данных не затрагиваются. - `BrowserRunsModule` подключает обработчик штатного закрытия NestJS для тестового среза: закрытие приложения не вызывает `Stop` у `running` браузеров, ждёт фоновые задачи ограниченное время и сохраняет неразрешённые `starting`/`stopping` как `recovery_required`; поздние результаты после дедлайна не перезаписывают состояние. API-тест проверяет сохранение и точное переподключение живого процесса, lifecycle-тесты — тайм-аут незавершённых Start/Stop. Обычный `main` пока не регистрирует этот модуль; аварийное завершение и настоящий runtime этим не подтверждены.
- D-002 для принятой границы MVP реализован: `API_HOST` принимает только literal `127.0.0.1` или `::1`; API проверяет точный `Host`, отклоняет дублированные заголовки и принимает только явно разрешённый `Origin`, обязательный для запросов, меняющих состояние. Vite proxy сохраняет адрес исходной страницы; fake API явно разрешает `http://127.0.0.1:5173`. ADR-0014 добавляет memory-only session cookie: `/health`, `/session` и `/docs*` публичны, остальные API-маршруты требуют сессию и возвращают `401` без неё. Это блокирует запросы чужих веб-страниц, но не аутентифицирует локальные программы: они могут вызвать `/session` и подделать заголовки. Защита от них не входит в принятую границу MVP.
- Ветка `v2/public-foundation` опубликована в origin; основные изменения Phase 3 и документация сохранены локальными коммитами, но пока не отправлены. В незакоммиченном состоянии оставлен непроверенный Windows process smoke-скрипт; он не входит в доказательства и коммиты. Удалённый CI текущего снимка не проверялся. Конфигурация CI содержит Ubuntu и Windows на Node.js `24.19.0`, основной набор тестов и `test:integration` со сборкой. Проверки текущего SQLite-набора и frozen install выполнены локально на Windows; удалённые результаты обеих ОС не подтверждены.
- Добавлены минимальные SQL migrations — явные миграции схемы — `schema_migrations`/`profiles`/`profile_code_sequence`/`browser_runs`, `SqliteProfileRepository` и `SqliteBrowserRunRepository` поверх общего Kysely/native SQLite handle. `ProfileRepository` выдаёт стабильный серверный `profileCode` через транзакционную последовательность; миграция заполняет коды для ранее сохранённых профилей и создаёт уникальный индекс. `BrowserRunService` подключает transition guard — проверку допустимых переходов — и `ProfileOperationMutex` к persistence; профильная занятость проверяется сервисом и SQLite. `BrowserRunRecoveryBarrier` сохраняется как read-only диагностический helper, но больше не блокирует запуск API; startup-тест проверяет, что `recovery_required` остаётся в базе без изменения. Ограниченный profile API и UI-сценарий создания профиля реализованы и проверены через NestJS/Fastify/React client; регистронезависимый поиск кириллицы использует зарегистрированную Unicode-функцию SQLite. Lifecycle-интеграция UI, process-aware recovery, управление процессами и настоящий адаптер ShardX ещё не реализованы. Каркас интерфейса не является готовой lifecycle-интеграцией.
- Принятые уточнения: [ADR-0009](adr/0009-durable-profile-occupancy.md) запрещает освобождать профиль при живом или неустановленном состоянии браузера; [ADR-0012](adr/0012-browser-run-occupancy.md) фиксирует отдельные runs и SQLite-инвариант; [ADR-0010](adr/0010-sqlite-exclusive-root-ownership.md) выбирает и реализует базовую эксклюзивную блокировку основного SQLite-соединения для единоличного владения `ANTIDETECT_HOME`; [ADR-0011](adr/0011-localhost-request-policy.md) фиксирует базовую Host/Origin-политику; [ADR-0013](adr/0013-profile-http-contract.md) принимает первый ограниченный профильный HTTP-контракт; [ADR-0014](adr/0014-local-session-boundary.md) фиксирует базовую session boundary. Базовый graceful shutdown — штатное завершение — теперь закрывает HTTP-приложение до root lock. Решение от 26.09.2026 не блокировать API из-за отдельной занятой записи проверяется локальным integration-тестом; process-aware recovery, более сильная OS authentication, Linux CI и платформенное поведение сигналов остаются открыты. В [плане](development-plan.md) создание/чтение профиля выполняется в Phase 2, API/UI-команды с подменным движком — в Phase 3.
- Корректировки аудита: `runMigrations()` до новых миграций отклоняет неизвестную версию, неверное имя и пропуск в истории; тесты проверяют обновление предыдущей схемы и откат неудачной миграции. Ошибка барьера содержит только `id`, `profileId`, `status`, а межпроцессный тест проверяет отсутствие внутренней информации в выводе и сохранность записи. Запросы занятости используют существующий частичный индекс; тесты проверяют план фактически выполненного запроса. Web использует общий contracts package и локальный proxy, а ShardX не скачивался и не запускался.
- Принят [ADR-0013](adr/0013-profile-http-contract.md): строгие контракты создания, чтения и ограниченного списка профилей, bounded search/sort, стабильная форма ошибок, session boundary и граница Host/Origin для несекретных profile metadata. Схемы, application service, API, SQL pagination/filter/sort, OpenAPI, HTTP-проверки и UI-сценарий создания реализованы в текущей рабочей ветке; более сильная local authentication остаётся обязательной границей перед секретами и управлением браузером.
- Следующие технические шаги: process-aware recovery и shutdown policy в Phase 3; базовый session gate остаётся. UI-команды проверяются только через отдельный fake-режим; ordinary runtime wiring отсутствует. CSRF/custom-header policy для state-changing чувствительных маршрутов и удалённый CI требуют отдельных проверок.

### Startup и application directories

`apps/api/src/main.ts` является composition root — местом связывания конфигурации и инфраструктуры. После проверки `API_PORT` он вызывает `resolveAppPaths()`, создаёт только `rootDir` и `dataDir`, получает `acquireRootOwnership()`, проверяет базу и выполняет миграции, затем создаёт остальные каталоги, выполняет `buildApp()` и `app.listen()`. Занятый run не является глобальным отказом старта и сохраняется в SQLite; startup integration test проверяет `/health=200` при `recovery_required`, а также отказ второго владельца до порта, продолжение работы владельца и повторный захват после его завершения.

При указании файла вместо корня `ensureAppRootDirectories()` завершает процесс с `ENOTDIR`, HTTP-порт не открывается, а исходный файл не заменяется. Это подтверждает fail-closed — остановку при небезопасной ошибке — на текущем startup-слое; Windows ACL, recovery и graceful shutdown остаются отдельными задачами.

ADR-0010 фиксирует и частично реализует порядок запуска: до миграций, продуктовых каталогов и открытия HTTP основное SQLite-соединение получает эксклюзивную блокировку корня и удерживает её до завершения API без длительной транзакции. Базовый guard и локальная startup integration-проверка проходят; `ApiRuntime` освобождает root только после успешного закрытия HTTP-приложения, а при ошибке или таймауте закрытия сохраняет блокировку fail-closed и завершает процесс с ошибкой по bounded shutdown policy — политике ограниченного завершения. После смерти процесса ОС освобождает lock, но profile recovery, платформенное поведение сигналов и Linux CI ещё не приняты.

ADR-0011 фиксирует базовую request policy: API привязан только к literal loopback, а Fastify hook проверяет ровно один `Host` и допустимый same-origin `Origin`. ADR-0014 добавляет memory-only session cookie для текущих product routes. Это снижает риск запросов с вредоносной страницы, но не является OS authentication — проверкой личности локального процесса, — поэтому доступ к секретам, Start/Stop и CDP требует отдельного решения.

### Обновление эксперимента ShardX в виртуальной машине от 2026-08-20

Пользователь отдельно разрешил одноразовый эксперимент только внутри `Win10`. В `C:\ShardX-Spike` загружен архив `@proxyshard/shardx@0.1.11` размером 48 595 байт; его SHA-512 был преобразован в SRI — строку контроля целостности — и совпал с опубликованным значением (`True`). SDK установлен из этого локального архива через `pnpm.cmd add 'file:.\shardx-0.1.11.tgz' --ignore-scripts`; install-скрипты при этом не запускались.

Первый вызов `new ShardX().listProfiles()` получил runtime — среду выполнения — и библиотеку отпечатков; вывод содержал непустой список и был сокращён терминалом как `... 700 more items`. Затем создан тестовый сохранённый profile и выполнен headful launch — запуск браузера с видимым окном. Пользователь подтвердил открытие `about:version` и `https://example.com`.

Штатный lifecycle — жизненный цикл — наблюдался через `BrowserSession`: `s.pid` и `s.process.pid` были `5892`, `process` являлся `ChildProcess` — объектом дочернего процесса Node.js, а после закрытия окна пришло событие `exit 0 null`. Повторный запуск того же сохранённого profile использовал ту же папку данных; это подтверждает сохранение записи profile, но ещё не persistence — сохранение именно браузерных данных, например cookie. Второй одновременный `launch()` того же profile не был отклонён и вернул `SECOND_LAUNCHED 4716`; второй сеанс был остановлен командой теста. Это доказывает отсутствие гарантии SDK «один активный запуск на profile», но не доказывает отсутствие всех возможных файловых блокировок.

21.08.2026 практическое выполнение Phase 0 закрыто как ограниченный evidence-spike: дополнительно наблюдались CDP с/без listener, отсутствие воздействия CDP-close на вручную запущенный foreign Chromium и orphan tree из шести Chrome-процессов после намеренного завершения launcher спустя пять секунд running. Это устанавливает архитектурные требования, но не является принятием runtime для production.

Непроверенные interrupted/concurrent first install, integrity закрытых архивов, reused PID, automatic recovery, рабочий proxy/external IP/DNS/QUIC/WebRTC и fingerprint surfaces перенесены в обязательные phase gates. Цепочка поставки не принята; одноразовое разрешение не является общим разрешением на повторную загрузку, обновление или запуск ShardX. Подробный протокол: [phase-0-shardx.md](spikes/phase-0-shardx.md).

## История: расхождения старого прототипа с целевой V2

Следующие пункты объясняют отказ от прототипа по ADR-0005. Они не описывают код `antidetect-v2-public` и не являются списком текущих дефектов её реализации.

1. Runner старого прототипа использовал Bablosoft, а не ShardX.
2. Состояние запуска хранится через `Profile.isOpen` и in-memory `Map`; durable double-start protection и recovery отсутствуют.
3. `LifecycleService` передаёт proxy в `LaunchOptions`, но `Runner.launch()` его не применяет и использует `loadProxy: false`. Успешная проверка proxy не доказывает, что browser запущен через proxy.
4. Proxy password хранится в SQLite открытым текстом.
5. Profile path строится из имени, а rename перемещает каталог. В v2 path должен строиться из UUID и не меняться при rename.
6. Fingerprint меняется на месте, тогда как target v2 предполагает immutable ShardX identity.
7. Корневой `src/` дублирует `packages/*`.
8. Предыдущая target architecture предлагала PostgreSQL, Redis/BullMQ и worker, что противоречит принятой v2 baseline.
9. Старые ADR фиксировали Playwright/FingerprintSwitcher runner и не являются действующими решениями v2.
