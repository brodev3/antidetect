## Краткий вывод

В полном Git-репозитории и исходной рабочей папке одновременно сохраняются legacy v1, незавершённая TypeScript-миграция legacy, незакоммиченные эксперименты и отдельная целевая архитектура v2. В V2-worktree legacy/prototype-код удалён, поэтому эти слои нельзя считать одним текущим приложением.

Antidetect v2 с ShardX пока не реализован.

### Начало Phase 1 от 2026-08-21

После отдельного `go` была создана локальная ветка `v2/foundation`, а затем отдельная публичная orphan-ветка — ветка без legacy-истории — `v2/public-foundation` в Git worktree — независимой рабочей папке — `C:\Disk_D\GitRepo\antidetect-v2-public`. Личные рабочие материалы в неё не переносятся.

Цель Phase 1 — создать V2-пакеты `apps/api`, `apps/web` и `packages/contracts` непосредственно в корне новой рабочей папки, а не поверх legacy-каталогов и не внутри `v2/`. В публичной ветке зафиксированы корневой `package.json`, pnpm workspace, lockfile, TypeScript baseline, пакет `@antidetect/contracts` с Zod health schema и tests, а также `@antidetect/api` с NestJS bootstrap, `HealthController`, FastifyAdapter, глобальным Zod bridge, OpenAPI JSON и проверенными `/health`/`/docs-json`. Предыдущий foundation checkpoint перед startup-слоем — `7d15524`; текущая ветка также содержит подготовку каталогов до открытия порта. Политика каталогов D-009 принята: `%LOCALAPPDATA%\\Antidetect` по умолчанию и `ANTIDETECT_HOME` для dev/test override, чистый resolver и `ensureAppDirectories()` реализованы и проверены, а Windows permissions остаются отдельным незакрытым слоем. Quality tooling включает Prettier, ESLint, TypeScript build в пакетные `dist/` и package start script; локальные format, lint, typecheck, 16 тестов и build проходят. CI skeleton содержит те же проверки, но удалённый запуск ещё не подтверждён. Отсутствуют `apps/web`, база данных, browser runtime и ShardX adapter. Dependency audit закрыт обновлением `@nestjs/swagger` до `11.4.7` и транзитивных пакетов: `pnpm audit --audit-level=moderate` и production-аудит не нашли известных уязвимостей. Legacy/prototype code исходной папки `antidetect` не переносился в публичную ветку; независимые изменения документации в исходной папке не являются частью v2.

### Startup и application directories

`apps/api/src/main.ts` является composition root — местом связывания конфигурации и инфраструктуры. После проверки `API_PORT` он вызывает `resolveAppPaths()`, затем `ensureAppDirectories()`, и только после успешной подготовки файловой структуры выполняет `buildApp()` и `app.listen()`. Реальный smoke test — короткая проверка запуска — с временным `ANTIDETECT_HOME` создал каталоги `config`, `data`, `profiles`, `runtime` и `logs`, а `GET /health` вернул `200`.

При указании файла вместо корня `ensureAppDirectories()` завершает процесс с `ENOTDIR`, HTTP-порт не открывается, а исходный файл не заменяется. Это подтверждает fail-closed — остановку при небезопасной ошибке — на текущем startup-слое; гонки процессов, Windows ACL, SQLite и recovery остаются отдельными задачами.

## Фактическое состояние среды Phase 0

Подтверждено 19 августа 2026 года до перезапуска основной системы:

- автоматические контрольные точки выключены;
- Enhanced Session — расширенный сеанс с перенаправлением ресурсов основной системы — отключён на системном и пользовательском уровнях;
- обмен данными и Guest Service Interface — интерфейс копирования файлов — отключены; прямые устройства, GPU — графический процессор, физические диски, подключённые COM-порты и вложенная виртуализация отсутствуют;
- установочный ISO-образ отключён, загрузчик Windows стоит первым, автоматический запуск виртуальной машины выключен;
- виртуальная машина подключена к отдельному Internal Switch — внутреннему коммутатору — `ShardX-Isolated`, а не к `Default Switch` или внешнему коммутатору;
- основной интерфейс изолированной сети использует `192.168.250.1/24` без IPv4-шлюза; пересылка пакетов и объявления маршрутов отключены;
- пользовательский `NAT` — трансляция сетевых адресов, статические пробросы, сетевой мост и фактически включённый общий доступ к интернету отсутствуют;
- на сетевом адаптере виртуальной машины действуют 14 `ACL` — правил контроля доступа: частные и служебные IPv4-диапазоны и весь IPv6 запрещены в обоих направлениях; защита DHCP и защита от объявлений маршрутизатора включены.

После отключения питания и перезапуска основной системы административно подтверждено, что `Win10` остаётся выключенной и все критичные параметры сохранились: поколение 2, Secure Boot включён, автоматический запуск выключен, тип контрольной точки `ProductionOnly`, фиксированные 8 ГБ памяти, четыре виртуальных процессора, вложенная виртуализация выключена, `ShardX-Isolated` подключён, 14 сетевых правил действуют, прямые устройства отсутствуют. Также повторно подтверждены адрес `192.168.250.1/24`, отсутствие IPv4-шлюза, отключённая пересылка и отсутствие `NAT` и статических пробросов.

После отдельного разрешения `Win10` успешно загрузилась в базовом сеансе без `NAT` и без ShardX. Внутри подтверждены Windows 10 Pro 22H2, сборка `19045.6456`, включённые Microsoft Defender и все профили межсетевого экрана. Адаптер получил только `169.254.38.33` — автоматический локальный адрес APIPA при отсутствии DHCP; IPv4-шлюз и маршрут по умолчанию отсутствуют. Установлены финальное обычное обновление `KB5066791` и пакет подготовки ESU `KB5072653`, но лицензии ESU Year 1–3 имеют состояние `Unlicensed` — не лицензировано. По [ADR-0006](adr/0006-phase-0-windows-10-residual-risk.md) это явный остаточный риск, принятый пользователем только для текущей одноразовой изолированной Phase 0; дата загрузки ISO-образа сама по себе не свидетельствует о повреждении или неправильном образе.

Автономные отрицательные сетевые тесты подтвердили отсутствие соединения из гостевой Windows с основной системой `192.168.250.1:445`, представителями частных IPv4-диапазонов, публичным IPv4 `1.1.1.1:443` и публичным IPv6. Во время работающей виртуальной машины основная Windows повторно показала адаптер `Status: Ok` на `ShardX-Isolated`, все 14 правил запрета, выключенные пересылку и объявления маршрутов для IPv4/IPv6, `NAT=0`, отсутствие статических пробросов и `ICS_ENABLED=0` — ни одно подключение не использует общий доступ к интернету. Служба `SharedAccess` находится в состоянии `Running` при типе запуска `Manual`, но сам общий доступ не включён.

Гостевой аудит дополнительно показал: `RemoteAccess` и `RemoteRegistry` отключены; SSH-сервер отсутствует; `WinRM` остановлен; RDP — удалённый рабочий стол — запрещён, и порт `3389` не прослушивается. До усиления SMB — сетевой доступ к файлам — прослушивал порт `445`, но пользовательских общих ресурсов не было. После этого `LanmanServer` и `vmicvmsession` — служба PowerShell Direct, прямого управления виртуалкой с основной системы — остановлены и отключены. Пользователь явно подтвердил, что после чистой установки не входил в личные аккаунты, не копировал личные файлы и не вводил пароли, ключи или данные прокси.

На основной Windows подтверждены сборка `26200.9168`, включённые антивирус, защита в реальном времени, поведенческий мониторинг и сетевая проверка угроз Microsoft Defender; сигнатуры обновлены 18 августа 2026 года, все три профиля межсетевого экрана включены. Перед созданием точки на `C:` было 126 ГБ свободно. При штатно выключенной `Win10` создана единственная исходная контрольная точка `pre-shardx-clean-baseline-2026-08-19` от 19 августа 2026 года, 23:16:48. Политика машины осталась `ProductionOnly`, а `Checkpoint-VM` завершилась успешно. `Get-VMSnapshot` сообщил `SnapshotType: Standard`; это поле использует другую классификацию без значения `Production` и не доказывает запасной переход к стандартной точке. Политика `ProductionOnly` запрещает такой запасной переход и при неудаче завершает создание ошибкой.

Аудит 20 августа 2026 года без загрузки файлов подтвердил официальный пакет `@proxyshard/shardx@0.1.11`, его открытый Node SDK — комплект разработки — и публичные условия личного использования. Пользователь определил Antidetect v2 как личный некоммерческий проект без продажи, публичного сервиса и распространения движка. Это закрывает лицензионную неопределённость только для текущего scope — границы проекта — но не проверку цепочки поставки. SDK при первом использовании получает закрытые engine, Widevine и fingerprint archives из изменяемого `main/runtime.json` и CDN — сети доставки содержимого; в просмотренном загрузчике нет проверки SHA-256 или цифровой подписи до распаковки. Диапазон `adm-zip ^0.5.16` затронут уязвимостью до исправленной версии `0.6.0`.

После отдельного разрешения применён временный `WinNAT` `ShardX-Temp` для `192.168.250.0/24`. В гостевой Windows вручную настроены `192.168.250.10/24`, шлюз `192.168.250.1` и DNS `1.1.1.1`. Базовые 14 правил запрета Hyper-V сохранены; для разрешения ARP — сопоставления IP-адреса с MAC-адресом — шлюза добавлены два более точных правила Allow для `192.168.250.1/32`. На основной Windows правило `ShardX VM block host IP` блокирует весь входящий IP-трафик от `192.168.250.10` к `192.168.250.1`. После удаления временного прямого маршрута `1.1.1.1/32` из гостя подтверждены `1.1.1.1:443 = True` и `192.168.250.1:445 = False`; маршрут основной Windows по умолчанию остаётся `xray_tun`. Это подтверждает рабочий выход VM через текущий Xray-маршрут и сохранённый запрет проверенного доступа к основной системе.

Этот вариант не является allowlist — списком явно разрешённых адресов: помимо заблокированных частных и служебных IPv4-диапазонов и IPv6 гостю доступен публичный IPv4. Внутри гостевой Windows установлены Node.js `24.19.0` и pnpm `11.16.0`; PowerShell блокирует `npm.ps1`, поэтому для bootstrap — первичной установки — использовались `npm.cmd` и `pnpm.cmd` без ослабления execution policy — политики выполнения сценариев.

### Обновление эксперимента ShardX в виртуальной машине от 2026-08-20

Пользователь отдельно разрешил одноразовый эксперимент только внутри `Win10`. В `C:\ShardX-Spike` загружен архив `@proxyshard/shardx@0.1.11` размером 48 595 байт; его SHA-512 был преобразован в SRI — строку контроля целостности — и совпал с опубликованным значением (`True`). SDK установлен из этого локального архива через `pnpm.cmd add 'file:.\shardx-0.1.11.tgz' --ignore-scripts`; install-скрипты при этом не запускались.

Первый вызов `new ShardX().listProfiles()` получил runtime — среду выполнения — и библиотеку отпечатков; вывод содержал непустой список и был сокращён терминалом как `... 700 more items`. Затем создан тестовый сохранённый profile и выполнен headful launch — запуск браузера с видимым окном. Пользователь подтвердил открытие `about:version` и `https://example.com`.

Штатный lifecycle — жизненный цикл — наблюдался через `BrowserSession`: `s.pid` и `s.process.pid` были `5892`, `process` являлся `ChildProcess` — объектом дочернего процесса Node.js, а после закрытия окна пришло событие `exit 0 null`. Повторный запуск того же сохранённого profile использовал ту же папку данных; это подтверждает сохранение записи profile, но ещё не persistence — сохранение именно браузерных данных, например cookie. Второй одновременный `launch()` того же profile не был отклонён и вернул `SECOND_LAUNCHED 4716`; второй сеанс был остановлен командой теста. Это доказывает отсутствие гарантии SDK «один активный запуск на profile», но не доказывает отсутствие всех возможных файловых блокировок.

21.08.2026 практическое выполнение Phase 0 закрыто как ограниченный evidence-spike: дополнительно наблюдались CDP с/без listener, отсутствие воздействия CDP-close на вручную запущенный foreign Chromium и orphan tree из шести Chrome-процессов после намеренного завершения launcher спустя пять секунд running. Это устанавливает архитектурные требования, но не является принятием runtime для production.

Непроверенные interrupted/concurrent first install, integrity закрытых архивов, reused PID, automatic recovery, рабочий proxy/external IP/DNS/QUIC/WebRTC и fingerprint surfaces перенесены в обязательные phase gates. Цепочка поставки не принята; одноразовое разрешение не является общим разрешением на повторную загрузку, обновление или запуск ShardX. Подробный протокол: [phase-0-shardx.md](spikes/phase-0-shardx.md).

- `packages/config`;
- `packages/core`;
- `packages/db`;
- `packages/runner`;

Решением от 18 августа 2026 года этот рефактор зафиксирован как **discarded prototype**: v2 создаётся с clean foundation, а код прототипа не переносится по умолчанию. Подробности: [ADR-0005](adr/0005-clean-v2-foundation.md).

Файлы прототипа сохранены в Git-снимке `cebcc68` и исходной ветке `spike/shardx-phase-0-vm`, отмеченной меткой `pre-v2-preservation-2026-08-19`. В V2-worktree они удалены 23.08.2026 после отдельного подтверждения; это удаление пока не зафиксировано коммитом.

### `preserved-drafts`

На момент первоначального аудита незакоммиченными были:

- `apps/api`;
- корневой `src/` и `tsconfig.json`;
- прежние черновики документации.

После явного разрешения они сохранены в локальном контрольном снимке. `apps/api` и корневой `src/` удалены из V2-worktree, но остаются историческими черновиками в локальной ветке и Git-истории.

`.vscode/`, `packages/db/s.zip` и `test.gz` остаются локальными незакоммиченными файлами только в исходной папке `antidetect`; V2-worktree их не содержит. `.env` также не включён и не читался.

Корневой `src/` частично дублирует и уже расходится с `packages/*`. До отдельного решения ни один из этих дублей нельзя удалять или автоматически объявлять источником истины.

Сохранённые черновики не являются foundation v2. Возможное точечное повторное использование требует отдельного разбора конкретного фрагмента по ADR-0005.

### `v2-target`

Целевая v2-архитектура описана активными документами в `docs/`:

- local-first control plane;
- ShardX как единственный пользовательский browser runtime;
- NestJS поверх Fastify и React;
- SQLite/Kysely;
- строгий lifecycle запусков;
- process recovery;
- SSE;
- security и failure-oriented tests.

Это согласованная цель, а не описание готового кода.

## Публичная Git-история

Ветка `v2/public-foundation` не имеет родительской истории; её первый root commit `13855ac` — корневой commit без родительской истории — содержит только public V2 files. Публичный кодовый ряд развивается отдельными foundation-коммитами; текущий startup-слой подготовки каталогов описан выше и не должен смешиваться с legacy/prototype. Local preservation branches и личные рабочие материалы не являются её предками и не публикуются вместе с v2.

## Критические расхождения с v2

1. Текущий runner использует Bablosoft, а не ShardX.
2. Состояние запуска хранится через `Profile.isOpen` и in-memory `Map`; durable double-start protection и recovery отсутствуют.
3. `LifecycleService` передаёт proxy в `LaunchOptions`, но `Runner.launch()` его не применяет и использует `loadProxy: false`. Успешная проверка proxy не доказывает, что browser запущен через proxy.
4. Proxy password хранится в SQLite открытым текстом.
5. Profile path строится из имени, а rename перемещает каталог. В v2 path должен строиться из UUID и не меняться при rename.
6. Fingerprint меняется на месте, тогда как target v2 предполагает immutable ShardX identity.
7. Корневой `src/` дублирует `packages/*`.
8. Предыдущая target architecture предлагала PostgreSQL, Redis/BullMQ и worker, что противоречит принятой v2 baseline.
9. Старые ADR фиксировали Playwright/FingerprintSwitcher runner и не являются действующими решениями v2.
