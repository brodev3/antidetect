# ADR-0009: занятость профиля до подтверждённого завершения браузера

> Статус: принятая цель; не реализовано
> Дата: 2026-09-05

## Контекст

Аудит обнаружил противоречие в целевой модели: потеря управления живым браузером могла переводить запуск в конечное состояние `failed`, а ограничение SQLite учитывало только `starting`, `running`, `stopping`. Ошибка управления освобождала бы профиль для нового запуска, хотя его каталог ещё мог использоваться браузером.

## Решение

- Занятость профиля — сохраняемый в SQLite запрет нового запуска и удаления — не снимается только из-за ошибки, истечения времени ожидания или потери объекта управления процессом.
- Конечные состояния `stopped` и `failed` допустимы после подтверждения, что принадлежащее запуску дерево процессов завершено либо запуск не успел создать процессы. Если создание процессов могло произойти, одного отсутствующего PID или объекта управления недостаточно.
- Пока состояние процессов не выяснено, профиль сохраняет занятость и после перезапуска API. Ошибка и причина блокировки доступны отдельно от утверждения «браузер завершён».
- Повторный Start и удаление занятого профиля отклоняются. Повторный Stop безопасен, но успешный ответ SDK сам по себе не подтверждает остановку.
- Восстановление учитывает все записи занятости, включая потерявшие управление процессы. Неизвестный процесс нельзя завершать по одному PID — идентификатору процесса.
- Ограничение SQLite и блокировка операций одного профиля в памяти обеспечивают один и тот же набор занятых состояний.

## Альтернативы и границы

Оставить `failed` конечным состоянием при живом браузере и проверять только три активных статуса — отклонено: правило повторного запуска становится небезопасным.

Считать любой оставшийся PID нашим и завершать его — отклонено: Windows может повторно использовать идентификатор для чужого процесса.

Этот ADR принимает инвариант, но не выбирает представление в таблицах: отдельное блокирующее состояние или отдельная запись занятости. Конкретная схема, ограничение SQLite и переходы должны быть согласованы по D-014 до миграции запусков. Способ безопасного управления потерянным процессом остаётся в D-001/D-006.

## Проверка реализации

До принятия реализации требуются воспроизводимые тесты с `FakeBrowserRuntime` — тестовой заменой движка — и настоящей временной SQLite:

1. Ошибка после создания процесса и неудачная очистка сохраняют занятость; повторный запуск и удаление отклоняются.
2. Перезапуск API не теряет эту блокировку.
3. Только подтверждённое завершение принадлежащего запуску дерева освобождает профиль.
4. Повторно использованный PID и чужой браузер не приводят к завершению чужого процесса или ложному освобождению профиля.

Тесты ещё не реализованы. Обновление документов не закрывает проверку ShardX или Windows; новые эксперименты требуют отдельного разрешения.
