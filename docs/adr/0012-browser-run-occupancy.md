# ADR-0012: отдельная запись занятости browser run

> Статус: принято для схемы, базового сервиса жизненного цикла и профильной занятости; первоначальная глобальная проверка при запуске API заменена решением от 2026-09-26; восстановление реальных процессов ещё не реализовано
> Дата: 2026-09-17

## Контекст

`profiles` хранит постоянную конфигурацию профиля, а запуск браузера имеет собственный lifecycle — жизненный цикл — и историю попыток. Если смешать их в одной таблице, невозможно безопасно хранить несколько завершённых запусков одного профиля и отдельно блокировать новый запуск при неопределённом состоянии процесса.

## Решение

1. Каждая попытка запуска получает отдельную запись в `browser_runs` и новый `id`. Запись `profiles` не переиспользуется как run history.
2. В Phase 2 фиксируется минимальный набор состояний:
   - блокирующие: `starting`, `running`, `stopping`, `recovery_required`;
   - конечные: `stopped`, `failed`.
3. SQLite partial unique index — частичный уникальный индекс — `browser_runs_one_active_per_profile` запрещает больше одной блокирующей записи для одного `profile_id`:

   ```sql
   UNIQUE(profile_id)
   WHERE status IN ('starting', 'running', 'stopping', 'recovery_required')
   ```

4. `browser_runs.profile_id` ссылается на `profiles.id`; `RootOwnership` включает SQLite foreign keys, поэтому запуск для неизвестного профиля отклоняется.
5. Repository не меняет status произвольно. `BrowserRunService` проверяет допустимые переходы и использует per-profile mutex — блокировку операций одного профиля — до записи через repository. Database constraint остаётся последней защитой от гонки и переживает перезапуск API.

## Failure paths

- Второй активный run одного профиля получает ошибку SQLite и не создаётся.
- `recovery_required` остаётся блокирующим: отсутствие доверенной process identity не освобождает профиль.
- Завершённые `stopped` и `failed` записи сохраняют историю и не занимают partial unique index.
- Неизвестный `profile_id` отклоняется foreign key до появления run.

## Границы решения

Сама миграция не реализует команды Start/Stop, проверку идентичности процесса или сверку записей запуска с процессами операционной системы. Read-only barrier только перечисляет занимающие профиль записи и не меняет их статус. Первоначально его подключили как глобальное условие готовности API; это поведение заменено 2026-09-26 по D-015: сохранённый run не закрывает HTTP-порт целиком, а занятость конкретного профиля сохраняется. В fake-only recovery точная идентичность и успешное переподключение переводят `recovery_required` обратно в занимающий статус `running`; неизвестный процесс остаётся в `recovery_required`. Это не доказывает, что настоящий Chromium завершён, и не разрешает автоматически переводить неопределённый процесс в конечный статус.

## Проверка

На настоящей временной SQLite проверены: один активный run на профиль, блокировка `recovery_required`, независимые профили, сохранение истории конечных запусков и отказ для неизвестного профиля. Прикладная проверка переходов, `BrowserRunService`, конкурентное создание записи запуска одного профиля, повторный переход в `stopped` и `BrowserRunRecoveryBarrier` покрыты тестами. Это ещё не доказательство управления реальными процессами или идемпотентной команды Stop. Исторический интеграционный тест старта API подтверждал отказ до открытия HTTP-порта при сохранённом `starting` run; 2026-09-26 его заменили проверкой, что API отвечает на `/health`, а существующая запись `recovery_required` остаётся неизменной. Идентификация и управление процессами остаются открытой частью Phase 3–5. Запросы занятости используют константные SQL-значения статусов для соответствия условию частичного индекса; внешний `profileId` остаётся связанным параметром запроса. План фактических запросов проверяется через `EXPLAIN QUERY PLAN`, а диагностическая ошибка не включает внутренние поля записи запуска.
