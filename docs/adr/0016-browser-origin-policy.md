# ADR-0016: проверка Origin браузерных запросов

> Статус: принято и реализовано
> Дата: 2026-09-27

## Контекст

API работает на loopback — локальном сетевом интерфейсе компьютера — и принимает команды, способные менять состояние профилей. Текущая UI-разработка открывается на `http://127.0.0.1:5173`, а API — на `http://127.0.0.1:3000`. Vite proxy — прокси-сервер разработки — раньше подменял `Origin` на адрес API, поэтому сервер не видел исходный адрес страницы.

Для MVP принята граница угроз: защищаться от запросов извне и чужих веб-страниц, но не заявлять защиту от программ, уже работающих на этом компьютере. Такой процесс может обратиться к публичному `/session` и подделать HTTP-заголовки.

## Решение

1. API продолжает принимать соединения только на literal loopback и проверять точный `Host`.
2. Если запрос содержит `Origin` — адрес страницы-источника браузерного запроса — он должен точно совпадать с одним origin из явного `allowedOrigins`. Если список не задан, разрешён только origin самого API. Тестовый API явно разрешает `http://127.0.0.1:5173`.
3. Запросы `POST`, `PUT`, `PATCH` и `DELETE` без `Origin` отклоняются с `403`. Чужой `Origin` также отклоняется до вызова контроллера. Безопасные методы `GET`, `HEAD` и `OPTIONS` могут обходиться без него.
4. Vite proxy сохраняет присланный браузером `Origin`; он не подставляет фиксированный адрес API.
5. Проверка Origin и session cookie — сессионной cookie — защищают браузерные маршруты от cross-site request forgery (CSRF) — подделки запроса с чужого сайта. Они не удостоверяют личность локального процесса и не заменяют защиту на уровне операционной системы.
6. Публичный `GET /session` остаётся bootstrap — начальной выдачей cookie. Любой процесс на компьютере может получить cookie; это принятое остаточное ограничение MVP.

## Причины

- Страница с чужого сайта не может установить разрешённый `Origin` в браузерном запросе, поэтому её изменяющие состояние запросы блокируются.
- Явный список не принимает автоматически aliases вроде `localhost`, другие порты, внешние домены или `null`.
- Отдельная OS-level authentication — проверка клиента средствами ОС — существенно расширила бы scope локального single-user приложения и всё равно требовала бы чёткой модели доверия между программами одного пользователя.

## Последствия и ограничения

- Политика не защищает от вредоносного ПО или произвольного процесса на этом компьютере: он может обратиться к API напрямую и сформировать разрешённые заголовки.
- Если UI в будущем окажется на отдельном production-origin, его нужно явно добавить в конфигурацию; wildcard не допускается.
- Внешняя automation — управление браузером скриптами — остаётся за пределами MVP и потребует отдельной модели доступа.

## Проверка

- API policy tests проверяют явный origin UI, отказ для неразрешённого origin и отказ для изменяющих состояние запросов без Origin.
- Profile и browser-run API tests передают разрешённый Origin.
- В UI-разработке запросы используют `/api` через Vite proxy без принудительной подмены Origin.
