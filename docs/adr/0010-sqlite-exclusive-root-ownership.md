# ADR-0010: единоличное владение корнем через SQLite

> Статус: принятое решение; базовая реализация и shared SQLite/Kysely boundary выполнены, интеграционные и переносимые проверки открыты
> Дата: 2026-09-14

## Контекст

Все данные одного экземпляра Antidetect v2 находятся под одним каноническим — однозначно вычисленным — `ANTIDETECT_HOME`: SQLite-база, каталоги профилей, runtime — среда выполнения — и логи. Два API-процесса, работающих с одним корнем, могут одновременно выполнить миграции, восстановление или запись файлов и повредить общую модель состояния.

Блокировка в памяти не подходит: каждый Node.js-процесс имеет собственную память. PID-файл — файл с идентификатором процесса — тоже недостаточен: он может остаться после аварии, а PID может быть повторно использован. Нужен межпроцессный механизм, который освобождается операционной системой при закрытии процесса и одинаково проверяется на поддерживаемых платформах.

SQLite уже является целевым хранилищем единственного локального API-процесса. Режим `locking_mode=EXCLUSIVE` позволяет соединению удерживать файловую блокировку базы до закрытия этого соединения. Он подходит для владения всем application root — корнем данных приложения — только при условии, что API получает блокировку до любой продуктовой работы с этим корнем.

## Решение

1. После `resolveAppPaths()` процесс создаёт только корень и каталог `data`, необходимые для открытия `data/antidetect.sqlite`. Создание файла базы при первом запуске считается технической подготовкой блокировки, а не разрешением выполнять миграции или продуктовые записи.
2. API открывает одно основное SQLite-соединение, устанавливает `PRAGMA locking_mode = EXCLUSIVE` и выполняет короткую проверку захвата, которая обязана фактически получить эксклюзивную блокировку. Предпочтительная форма проверки — короткие `BEGIN EXCLUSIVE` и `COMMIT`; точное поведение подтверждается межпроцессным тестом с выбранным SQLite-драйвером.
3. Ожидание блокировки ограничено небольшим временем. `SQLITE_BUSY` или эквивалентная ошибка преобразуется в понятную startup-ошибку — ошибку запуска — `APP_ROOT_IN_USE`. Проигравший процесс завершается без миграций, создания остальных продуктовых каталогов, восстановления и `app.listen()`.
4. После успешного захвата то же соединение должно выполнять миграции и обслуживать persistence — сохранение данных. Оно остаётся открытым до конца работы API. Длительная транзакция для удержания владения запрещена: удерживается файловая блокировка соединения, а не незавершённая бизнес-транзакция. Kysely создаётся над тем же native handle и проверяется запросом `select 1`; `runMigrations()` применяет явные SQL-миграции, а repository использует тот же database boundary — границу доступа к базе.
5. Только владелец создаёт остальные каталоги, выполняет recovery — сверку и восстановление состояния, — строит NestJS-приложение и начинает принимать HTTP-запросы. Полученная блокировка означает владение корнем, но не означает, что сохранённые профили безопасно готовы к запуску.
6. При штатном завершении API сначала перестаёт принимать новые команды, выполняет согласованное завершение и сохранение состояния, затем закрывает SQLite-соединение последним ресурсом корня. Базовое владение корнем реализовано; политика завершения управляемых браузеров частично проверена только в тестовом `BrowserRunsModule` по ADR-0015 и остаётся открытой для обычного `main` и реального runtime в D-015.
7. При аварийном завершении операционная система закрывает файловый дескриптор и освобождает SQLite-блокировку. Следующий процесс может получить владение, но до открытия HTTP обязан выполнить recovery — сверку и восстановление состояния. Повторное владение не снимает сохраняемую занятость профилей из ADR-0009.

Механизм является частью startup/infrastructure boundary — границы запуска и инфраструктуры. Domain/application code — предметная и прикладная логика — не зависит от SQLite-способа блокировки.

## Отклонённые альтернативы

- Обычный PID- или marker-файл — файл-маркер — отклонён как самостоятельная блокировка: требуется собственная проверка устаревания, PID может быть повторно использован, а авария оставляет файл.
- `proper-lockfile` и похожая heartbeat-модель — периодическое подтверждение жизни владельца — переносимы, но добавляют зависимость, интервалы обновления и эвристику устаревания. Для единственного процесса с уже обязательной SQLite это лишний второй источник владения.
- Именованный mutex — системная блокировка — хорошо подходит Windows, но привязывает основной механизм к одной ОС. Локальный socket/pipe — канал межпроцессного обмена — имеет отличающиеся правила имён и очистки на разных платформах.
- Транзакция, открытая на весь срок работы API, отклонена: она смешивает владение процессом с атомарностью бизнес-операции, мешает обычным транзакциям и усложняет корректное завершение.

## Последствия

Положительные последствия:

- аварийное завершение не оставляет доверенный stale lock — устаревший файл блокировки;
- не требуется отдельная рабочая зависимость только для владения корнем;
- миграции, repository — слой доступа к данным — и владение используют одно соединение и один источник координации;
- механизм не основан на Windows-specific API — интерфейсе, доступном только в Windows.

Ограничения и цена решения:

- сторонний процесс не должен напрямую открывать рабочую базу, пока API владеет корнем; диагностика и backup — резервное копирование — должны выполняться через владельца либо при остановленном API;
- параллельные SQLite-соединения внутри приложения нельзя добавлять без отдельной проверки их взаимодействия с эксклюзивным режимом;
- недоступная, повреждённая или занятая база делает весь корень недоступным, и API завершается fail-closed — без продолжения в небезопасном режиме;
- выбор SQLite journal mode — режима журнала — и стратегия резервного копирования остаются отдельными решениями persistence-слоя;
- принятое решение не закрывает D-002, представление сохраняемой занятости D-014 и полную семантику shutdown/recovery в D-015.

## Проверка реализации

Базовая реализация и локальный startup integration gate проверены автоматически с настоящей временной SQLite:

- `acquireRootOwnership()` отвергает второй владелец того же корня и возвращает `AppRootInUseError` с кодом `APP_ROOT_IN_USE`;
- закрытие первого соединения освобождает корень для следующего владельца;
- независимые временные корни можно владеть одновременно;
- отдельный Node.js-процесс получает блокировку, второй процесс завершается на `SQLITE_BUSY`, после принудительного завершения владельца следующий процесс снова получает корень.
- собранный `main.js` запускается в двух реальных API-процессах: первый отвечает на `/health`, второй завершается до открытия своего порта, первый продолжает отвечать, а после его завершения новый процесс снова запускается с тем же root.
- `createAppDatabase()` использует native handle из `RootOwnership`; `app.database.test.ts` выполняет `select 1`, закрывает root ownership и подтверждает, что последующий запрос через Kysely завершается ошибкой, то есть второго SQLite-соединения нет.

Остаются обязательными следующие проверки до закрытия D-015:

1. Первый API получает корень и продолжает отвечать; второй API с тем же корнем завершается с `APP_ROOT_IN_USE`, не открывает HTTP-порт, не выполняет миграции и не создаёт продуктовые данные.
2. Два API с разными временными корнями работают одновременно и не затрагивают реальные пользовательские данные.
3. После штатного закрытия первого процесса второй получает тот же корень.
4. После принудительного завершения владельца блокировка освобождается ОС, новый процесс получает корень и выполняет recovery до готовности API.
5. Ошибка прав, файл вместо каталога, повреждённая база и занятая база завершают startup без fallback на другой корень.
6. Проверки проходят на целевой локальной ОС и в Linux CI — среде непрерывной интеграции — с одной версией нативной SQLite-зависимости и одинаковой наблюдаемой семантикой.

Пока recovery, Linux CI и graceful shutdown не закрыты, ADR подтверждает базовый guard и локальный startup-порядок, но не полную переносимую гарантию готовности API.
