# ADR-0001: Модульная монорепа (apps + packages)
Статус: Superseded by [ADR-0003](0003-v2-local-control-plane.md)

Дата: 2025-09-25

Автор: @you

> Исторический ADR незавершённой миграции v1. Общая идея modular monorepo сохранена, но topology, queue/worker direction и конкретные boundaries не определяют v2.

## Контекст

Текущий проект — консольное приложение на Node.js, управляющее профилями браузера с антидетект-настройками (Playwright + fingerprints), хранением состояния (Google Sheets), простым CLI. В планах: типобезопасность (TypeScript), изоляция домена, расширяемость (плагины/интеграции), очереди задач, API и (в перспективе) UI-панель/десктоп-обёртка.

Нужна архитектура, позволяющая:

- Разделить доменную логику от инфраструктуры и исполняемых приложений
- Делиться типами/схемами между CLI, API, воркерами и UI
- Вести инкрементальную миграцию на TypeScript без «большого взрыва»
- Подключить очереди (BullMQ/Redis), API (Fastify/Nest), UI (Next.js/Tauri) без слома ядра
- Единообразно настраивать линт, форматирование, тесты и релизы

## Решение

Принять модульную монорепу с рабочими пространствами и общей конфигурацией:

```
apps/
  api/        # HTTP API (Fastify/Nest) — позже
  cli/        # CLI-утилита, замена/надстройка над текущим интерфейсом
  web/        # Next.js панель — позже (опционально)
packages/
  core/       # Домен: Profile/Proxy/Engine/use-cases/порты
  runner/     # Обёртка над Playwright + fingerprints (изолированно от домена)
  db/         # Доступ к данным (изначально Google Sheets; позже Prisma)
  queue/      # Абстракция очередей (BullMQ) — позже
  shared/     # Общие типы, zod-схемы, утилиты
  config/     # Загрузка конфигов/env с валидацией
```

Технические опоры:

- Менеджер пакетов: pnpm workspaces
- TypeScript project references (быстрые сборки и IDE-подсказки)
- Единый ESLint/Prettier/Husky/lint-staged на корне
- CI: GitHub Actions (lint/test/build/release)
- Версионирование/релизы: semantic-release (в перспективе)

Важно: стартовать минимально — задокументировать, затем создать каркас директорий, не меняя поведение. Миграцию JS→TS вести пошагово, начиная с «обёрточных» слоёв и общих типов, не переписывая всё сразу.

## Альтернативы

1) Оставить single-package: ниже порог входа, но масштабируемость и повторное использование проседают (API/UI/воркеры делить сложнее).
2) Multi-repo: хорош для больших команд, но избыточен здесь; сложнее шарить типы и синхронизировать версии.
3) Nx/Turborepo: дают кэш/оркестрацию, можно добавить позже; для старта достаточно pnpm + TS refs.

## Последствия

Плюсы:

- Чистые границы между доменом, инфраструктурой и приложениями
- Общие типы/схемы без дублирования
- Проще подключать новые интерфейсы (API/UI/desktop) и воркеры

Минусы/Риски:

- Больше начальной настройки (workspaces, TS refs, скрипты)
- Требуется дисциплина границ (не пересекать слои напрямую)

## Пошаговая миграция (инкрементально)

1) Каркас монорепы и базовые конфиги (без логики)
2) Выделить `packages/shared` для типов/схем (Zod) — начать типизацию с границ
3) Вынести Playwright-логику в `packages/runner` без изменения поведения
4) Постепенно переносить доменные операции в `packages/core`
5) Сформировать `apps/cli` поверх core/runner; сохранить текущие UX-потоки
6) При необходимости — `apps/api` (CRUD/оркестрация), затем очереди и UI

## Нерешённые вопросы (для последующих ADR)

- Выбор API-фреймворка (Fastify vs Nest) и auth-механизм
- Очереди (BullMQ) и стратегия ретраев/идемпотентности
- Переезд с Google Sheets на БД (Prisma; SQLite/Postgres)
- Плагинная модель поставщиков прокси и стратегий fingerprint
- Десктоп-упаковка (Tauri) и стратегия автообновлений
