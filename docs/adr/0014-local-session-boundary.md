# ADR-0014: локальная сессионная граница API

> Статус: принято и реализовано для текущих profile routes
> Дата: 2026-09-22

## Контекст

ADR-0011 защищает localhost API от запросов браузерной страницы через точные `Host`/`Origin`, но эти заголовки может сформировать любой локальный процесс. Для текущего несекретного profile API нужна дополнительная граница браузерной сессии без хранения секрета в `localStorage` и без заявления, что API получил полноценную авторизацию операционной системы.

## Решение

1. API выдаёт случайный непрозрачный токен длиной 32 байта только при первом обращении или после невалидной сессии. В состоянии сервера хранится только его SHA-256 digest — хеш-отпечаток; исходный токен не сохраняется в SQLite, логах или документации и существует лишь как transient — временное значение — для заголовка ответа.
2. `GET /session` является публичным bootstrap-маршрутом — начальной выдачей сессии — и отвечает `204` с cookie `antidetect_session`:
   - `Path=/`;
   - `HttpOnly`, чтобы JavaScript не мог прочитать значение cookie;
   - `SameSite=Strict`, чтобы браузер не отправлял cookie в cross-site контексте;
   - без `Domain`, поэтому cookie не расширяется на другие hosts.
3. Сейчас API работает по HTTP на loopback, поэтому `Secure` не ставится: браузер иначе не отправит cookie по текущему HTTP-сценарию. При переходе на HTTPS cookie должна получить `Secure`, а предпочтительно и `__Host-`-префикс.
4. `/health`, `/session` и `/docs*` остаются публичными. Все остальные текущие и будущие API-маршруты требуют валидную cookie-сессию после прохождения ADR-0011. Отсутствующая, неверная или неоднозначная cookie получает `401 Unauthorized`; дублированные `Host`, `Origin` и `Cookie` получают `403 Forbidden`.
5. Web API client перед каждым profile-запросом вызывает `/session`, затем использует `credentials: "include"`. Сервер не выдаёт состояние профиля через session endpoint.

## Почему так

- Непрозрачный токен проще отозвать перезапуском API и не раскрывает данные профиля.
- Хеш в памяти ограничивает ущерб от диагностического снимка памяти по сравнению с хранением исходного значения.
- `HttpOnly` убирает прямое чтение cookie из JavaScript, но не останавливает XSS от выполнения запросов из уже открытой страницы.
- `SameSite`, точный `Host` и обязательная проверка `Origin` для меняющих состояние запросов по ADR-0016 являются слоями защиты, а не доказательством личности локального процесса.

## Ограничения и остаточный риск

- Любой процесс на той же машине всё ещё может отправить допустимые заголовки и вызвать публичный `/session`; это не OS authentication и не защита от malware.
- Перезапуск API инвалидирует старую session cookie. UI должен получить новую сессию и повторить обычный GET.
- Тестовые Start/Stop routes в отдельной композиции также используют session cookie, но это не разрешает подключать их к обычному `main`. До реальных browser-control routes и proxy credentials требуется отдельное решение доступа и обработки секретов; CDP и process recovery тоже остаются открытыми.
- HTTPS, `Secure`/`__Host-` cookie, CSRF-защита state-changing routes и более сильная локальная идентичность клиента остаются отдельными будущими шагами.

## Проверка

- API-тест проверяет `401` без cookie, `204` и атрибуты `Set-Cookie`, доступ с валидной cookie и отказ с неверной cookie.
- Профильные black-box тесты получают сессию через `/session` перед каждым защищённым запросом.
- Web client tests проверяют отдельный bootstrap-запрос и передачу `credentials: "include"`.
- Полный session token не попадает в тестовые ожидания, логи или ответы API.
