# ADR-0013: HTTP-контракт профилей и граница доступа Phase 2

> Статус: принято; Zod-контракты, HTTP-маршруты и bounded search/sort реализованы
> Дата: 2026-09-21

## Контекст

В Phase 2 требуется первый сквозной продуктовый сценарий: создать профиль через API — программный интерфейс — и прочитать его после перезапуска. До реализации маршрутов необходимо зафиксировать входные и выходные данные, ограничения списка, ошибки и допустимую на этом этапе границу доступа. Иначе UI, контроллер и repository могут получить разные неявные контракты.

Профиль в этом сценарии является сохраняемой конфигурацией. Он ещё не доказывает готовность ShardX, наличие браузерного процесса или возможность Start/Stop.

## Решение

### Создание

- `POST /profiles` возвращает `201`.
- Клиент передаёт строгий JSON-объект только с `displayName`.
- `displayName` обрезается по краям и после этого должен содержать от 1 до 100 символов.
- Одинаковые отображаемые имена разрешены: идентичностью записи является серверный UUID, а имя остаётся пользовательской подписью.
- Сервер создаёт UUID, UTC timestamps — временные метки — и явно тестовую ссылку `identityRef` вида `test-identity:<profileId>`. Она не подтверждает интеграцию с ShardX.

### Чтение одной записи

- `GET /profiles/:profileId` принимает только UUID.
- Существующая запись возвращается с `200`.
- Отсутствующий корректный UUID возвращает `404` и код `PROFILE_NOT_FOUND`.

### Список

- `GET /profiles` использует `limit=50` и `offset=0` по умолчанию.
- `limit` ограничен диапазоном `1..100`; `offset` является неотрицательным safe integer — целым числом, точно представимым в JavaScript.
- Необязательный `search` обрезается по краям и ищет подстроку без учёта регистра только в `displayName`; пустое значение не фильтрует список.
- `sortBy` принимает только `createdAt` или `displayName`, а `sortOrder` — только `asc` или `desc`. По умолчанию используются `createdAt ASC`.
- Порядок стабилен: сначала выбранное поле и направление, затем `id ASC` как tie-breaker — дополнительное поле для однозначного порядка.
- Ответ имеет форму `{ items, nextOffset }`; `nextOffset` равен `null`, когда следующей страницы нет. Точный `total` в этот сценарий не входит.

### Ответ и ошибки

Публичная запись профиля содержит только:

- `id`;
- `displayName`;
- `identityRef`;
- `createdAt`;
- `updatedAt`.

Отдельный `profile.status` не добавляется: состояние запуска выводится из `browser_runs` и проверенного состояния процесса.

Ошибки этого сценария используют envelope — единую внешнюю оболочку — `{ error: { code, message } }`. На первом шаге зафиксированы коды `VALIDATION_ERROR` и `PROFILE_NOT_FOUND`; сообщение ограничено безопасным публичным текстом. Неизвестные поля строгих запросов и ответов отклоняются.

### Граница доступа

Для этих трёх ограниченных маршрутов с несекретными metadata — метаданными — принята текущая политика ADR-0011: literal loopback, один ожидаемый `Host` и точное совпадение присутствующего `Origin`. Принимается остаточный риск: другой локальный процесс пользователя всё ещё может вызвать создание или чтение профиля.

Local authentication — локальная проверка клиента — остаётся обязательным hard gate — условием допуска — до API прокси и их credentials, удаления профиля, Start/Stop, CDP и других чувствительных либо разрушительных операций.

## Failure paths

- Пустое, пробельное, слишком длинное имя или неизвестное поле отклоняются как `VALIDATION_ERROR` до application service.
- Неверный UUID отклоняется валидацией; корректный UUID без записи возвращает `PROFILE_NOT_FOUND`.
- Неверные, дробные, отрицательные, выходящие за границы или неразрешённые `search`/`sort` параметры отклоняются до SQL-запроса.
- Внутренние пути, состояние SQLite и stack trace не входят в публичную ошибку.

## Границы решения

ADR не реализует UI, local authentication, ShardX, proxy, delete, Start/Stop или CDP. Эти части требуют отдельных проверяемых шагов и соответствующих открытых решений D-001–D-008/D-010.

## Проверка

Zod-схемы и типы находятся в `packages/contracts`. Tests — проверки — покрывают строгий create-вход, UUID и timestamps ответа, error envelope, значения по умолчанию и границы списка, safe integer, search/sort allowlist, преобразование входной и выходной схемы списка в JSON Schema, реальные SQL-фильтр/сортировку, status codes, OpenAPI, сохранение после повторного запуска, `Host`/`Origin` и отсутствие лишних полей. UI и local authentication остаются отдельными следующими границами.
