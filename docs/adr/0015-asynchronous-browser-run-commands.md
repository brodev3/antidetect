# ADR-0015: асинхронные команды запуска и остановки

> Статус: принято и локально проверено для отдельного тестового API-среза с FakeBrowserRuntime; обычный `main` и реальные процессы остаются вне этого решения
> Дата: 2026-09-23

## Контекст

Синхронный HTTP-запрос ждал завершения `runtime.launch()` или `runtime.stop()`. Зависший запуск задерживал и ответ Start, и поставленный за ним Stop. Чтение только блокирующего запуска теряло последний результат `failed` или `stopped` после обновления интерфейса.

## Решение

1. Start сохраняет новый `browser_run` со статусом `starting` и возвращает `202 Accepted` с его идентификатором и `Location` на `GET /profiles/:profileId/run`. Фоновая задача переводит запись в `running`, `failed` либо `recovery_required`. `202` не доказывает успешный запуск браузера.
2. Повторный Start при блокирующем запуске получает `409 ACTIVE_BROWSER_RUN_CONFLICT` без второго вызова движка.
3. Stop во время `starting` быстро получает `409 BROWSER_RUN_START_IN_PROGRESS`; намерение остановки не ставится в очередь. После перехода в `running` клиент может повторить Stop.
4. Stop из `running` сохраняет `stopping` и возвращает `202`; повторный Stop при `stopping` получает тот же запуск и `202`, не вызывая движок второй раз. Stop после конечного состояния или до первого запуска возвращает `200` с последним запуском либо `null`.
5. Stop при `recovery_required` получает `409 BROWSER_RUNTIME_RECOVERY_REQUIRED`. Нельзя завершать процесс по одному PID или освобождать профиль без подтверждения.
6. GET возвращает последний созданный запуск, в том числе конечный. При одинаковом `created_at` порядок определяет SQLite `rowid` — порядок вставки записи.
7. У вызовов движка есть отдельные сроки ожидания. При истечении срока занятость сохраняется как `recovery_required`; поздний ответ всё ещё отслеживается. Поздно появившийся процесс проходит попытку штатной очистки, а конечное состояние записывается только после подтверждённого завершения.
8. При штатном закрытии API работающий браузер не останавливается. Модуль закрывает приём HTTP-команд, ждёт фоновые Start/Stop до ограниченного срока, переводит оставшиеся `starting`/`stopping` в `recovery_required`, затем снимает подписки на выход процессов. После дедлайна поздние ответы не меняют сохранённое состояние и не запускают дополнительный Stop. Длительность ожидания по умолчанию — 5 секунд; незавершённая занятость остаётся в SQLite.

## Почему так

Интерфейс уже показывает `Starting` и `Stopping`. Короткие HTTP-запросы не зависят от длительности операций движка, а GET остаётся источником состояния после обновления страницы. Альтернатива — синхронный `200` после полного выполнения — проще для клиента, но оставляет запрос открытым при зависании и затрудняет повторные команды.

## Ограничения и проверка

- Тестовый `BrowserRunsModule` подключается только при явной передаче сервиса в `buildApp()`. Обычный `main` не включает маршруты Start/Stop.
- Локальные тесты проверяют конфликт Start, быстрый отказ Stop во время запуска, повторный Stop, сроки ожидания, поздний результат и чтение конечного состояния. FakeBrowserRuntime не является доказательством поведения ShardX или дерева процессов Windows.
- Тесты FakeBrowserRuntime проверяют, что закрытие модуля оставляет `running` процесс живым, восстанавливает его после пересоздания приложения, ограниченно ждёт фоновые операции, сохраняет неопределённый `starting`/`stopping` как `recovery_required` и игнорирует поздние ответы после закрытия.
- Это не закрывает весь D-015: обычный `main` пока не создаёт сервис жизненного цикла и не подключает маршруты управления браузером или восстановление; аварийное завершение без обработчика NestJS, идентичность процесса и поведение настоящего ShardX/ОС остаются непроверенными. Браузерный Origin gate D-002 принят по ADR-0016; остаются независимые runtime/recovery проверки.
