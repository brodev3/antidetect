# Статический аудит доставки ShardX SDK 2.0.3

> Дата проверки: 2026-09-27
> Статус: ограниченный статический аудит; D-008 остаётся открытым
> Область: опубликованный исходный код тега `v2.0.3` и документация ProxyShard. Архивы runtime не скачивались, установка и запуск не выполнялись.

## Краткий вывод

SDK автоматически загружает закрытый движок и библиотеку отпечатков из сети. Список версий и ETag — меток версии HTTP-ресурса — берётся из `runtime.json` на изменяемой ветке `main`; независимая криптографическая проверка подлинности скачанных архивов в просмотренном загрузчике не обнаружена. На Windows архивы распаковывает `adm-zip`, а папка прежнего движка удаляется до загрузки новой. Этого достаточно, чтобы оставить установку, целостность и обновление движка непринимаемым риском, но недостаточно, чтобы утверждать о компрометации поставщика или доказанной удалённой эксплуатации.

## Подтверждённые факты

1. В теге `v2.0.3` файл `sdks/node/package.json` задаёт версию SDK `2.0.3`, лицензию SDK MIT и зависимость `adm-zip: ^0.5.16`. Диапазон `^0.5.16` не включает `0.6.0`.
2. `sdks/node/src/runtime.ts` получает манифест по адресу `https://raw.githubusercontent.com/ProxyShard/ShardBrowser/main/runtime.json`, а архивы — с `https://pub-e57a7c60f6934eb09a6600bf2fc59cdc.r2.dev`. Манифест не привязан в коде SDK к commit или подписанному релизу.
3. Загрузчик сравнивает сохранённые метки/версию движка с полями удалённого манифеста. При загрузке архива он сохраняет `ETag` ответа CDN, но просмотренный код не сравнивает его с ожидаемым ETag из манифеста и не проверяет независимую цифровую подпись или криптографическую контрольную сумму содержимого до распаковки. Сам по себе ETag не является подтверждённой здесь подписью издателя.
4. На Windows загрузчик вызывает `new AdmZip(tmp).extractAllTo(dest, true)` как для архива движка, так и для библиотеки отпечатков. На macOS/Linux движок распаковывается системной командой `unzip`.
5. Перед загрузкой обновлённого движка код удаляет старый каталог движка через `rmSync`, затем скачивает и распаковывает новый архив непосредственно в каталог кэша. Staging-каталог с атомарным переключением версии и откатом старой установки для движка в просмотренном пути не обнаружены. Поведение при конкурирующих установках отдельно не проверялось.
6. GitHub Advisory для `adm-zip` указывает затронутые версии `<0.6.0` и исправленную `0.6.0`, но текст описания отдельно говорит «до 0.5.18». Это расхождение в самом advisory. Точный пакет `adm-zip`, разрешённый конкретным lockfile опубликованного SDK, и достижимость описанного отказа в его сценарии этим статическим аудитом не подтверждены.
7. Документация ProxyShard называет SDK MIT, но отдельно указывает, что движок — закрытый бинарный продукт: личные проекты перечислены среди допустимых вариантов, а коммерческое использование движка в антидетект-, браузерном или fingerprint-spoofing-продукте запрещено без согласования. MIT-лицензия SDK сама по себе не является лицензией движка.

## Повторная проверка advisories от 2026-09-27

Проверены только страницы GitHub Advisory Database и заметки к выпускам `adm-zip`; npm-пакет и runtime-архивы не скачивались.

- [CVE-2026-77301](https://github.com/advisories/GHSA-7q85-xj36-vmfc) помечает уязвимыми версии `adm-zip <0.6.1` и исправленной — `0.6.1`. В исходнике SDK `v2.0.3` объявлен диапазон `^0.5.16`, который не допускает `0.6.1`; какой именно `adm-zip` попадает в опубликованный npm-пакет SDK, неизвестно.
- [CVE-2026-76845](https://github.com/advisories/GHSA-vwc7-r8mq-g2x9) перечисляет диапазон `>=0.5.9 <=0.6.0` как затронутый и не указывает исправленную версию. При этом заметки upstream-выпуска [`adm-zip v0.6.1`](https://github.com/cthackers/adm-zip/releases) заявляют блокировку записи через символические ссылки при распаковке. Это расхождение не закрыто: исходный код/тесты исправления и статус advisory отдельно не проверялись.
- Для [CVE-2026-39244](https://github.com/advisories/GHSA-xcpc-8h2w-3j85) поля advisory указывают `<0.6.0` и `0.6.0`, но описание говорит `before 0.5.18`; заметки выпуска `v0.6.0` называют этот CVE исправленным. Точную уязвимую/исправленную версию нужно сверить с опубликованным деревом зависимостей SDK.

Документация npm описывает подписи и provenance (проверяемое происхождение npm-пакета и сведения о его сборке) для самого пакета. Из этого и зафиксированного выше отдельного скачивания runtime-архивов следует: проверка npm-пакета сама по себе не подтверждает подлинность движка и библиотеки отпечатков, скачиваемых позднее; для них нужна отдельная подпись/контрольная сумма из закреплённого источника и проверка до распаковки.

## Сверка исходников тега `v2.0.3` от 2026-09-28

Официальный исходник [тега `v2.0.3`](https://github.com/ProxyShard/ShardBrowser/tree/6c3f65a04bac5a476a20bd0b6a68e93f2802bfe9/sdks/node) внутренне несогласован:

- [`package.json`](https://github.com/ProxyShard/ShardBrowser/blob/6c3f65a04bac5a476a20bd0b6a68e93f2802bfe9/sdks/node/package.json) называет пакет `@proxyshard/shardx` версией `2.0.3` и объявляет `adm-zip: ^0.5.16`.
- [`package-lock.json`](https://github.com/ProxyShard/ShardBrowser/blob/6c3f65a04bac5a476a20bd0b6a68e93f2802bfe9/sdks/node/package-lock.json) на том же commit называет корневой пакет версией `2.0.1` и фиксирует `adm-zip 0.5.17` с integrity hash.
- Поэтому lockfile в исходнике не подтверждает точное дерево зависимостей опубликованного npm-архива `2.0.3`. Страница/ответ реестра npm не предоставили доступ к точным metadata архива в этой проверке; tarball не скачивался.

Вывод ограничен: исходники релиза подтверждают объявленный диапазон зависимости, но точный состав опубликованного артефакта и его происхождение остаются непроверенными. D-008 остаётся открытым; этот шаг не разрешает загрузку, установку или запуск ShardX.

## Риски и границы вывода

- Изменяемый манифест и отсутствие независимой проверки архива создают риск цепочки поставки. Это не доказательство, что текущий CDN или репозиторий скомпрометирован.
- Диапазон `adm-zip` требует письменного уточнения или исправленного релиза, однако advisory внутренне противоречив, а точный установленный пакет в этом шаге не исследовался. Поэтому не заявляем, что конкретная установка точно уязвима.
- Удаление старого движка до скачивания нового создаёт риск отсутствующей или неполной установки при сбое. Реальный сбой обновления и межпроцессная гонка не воспроизводились.
- Закрытый runtime и условия его распространения требуют отдельной проверки, если scope выйдет за рамки личного некоммерческого проекта.
- Просмотр исходника тега подтверждает только его содержание на момент проверки. Он не подтверждает соответствие опубликованного npm-архива этому исходнику или составу зависимостей в конкретной установке.

## Решение и критерии закрытия D-008

D-008 остаётся открытым. Этот документ фиксирует наблюдения, но не разрешает загрузку, установку или запуск ShardX. Для повторного рассмотрения нужны:

1. Точный lockfile/SBOM опубликованного SDK и подтверждение исправленной версии `adm-zip` либо проверяемое объяснение несоответствия advisory.
2. Зафиксированный источник версии runtime и независимая проверка подлинности каждого архива до распаковки (например, подпись или контрольная сумма из отдельного доверенного релизного канала).
3. Безопасная стратегия обновления: временная установка, проверка, атомарное переключение/откат и сериализация конкурирующих установок; затем воспроизводимые проверки отказа и восстановления.
4. Ясность условий использования для выбранного сценария распространения проекта.
5. Только после отдельного разрешения — ограниченный эксперимент в допустимой изолированной среде. Он должен проверять фактический опубликованный пакет и поведение runtime; этот документальный аудит такого разрешения не даёт.

## Дополнение: проверка точного npm-архива 2.0.3 (2026-09-28)

На момент этой проверки 2026-09-28 архивы среды выполнения не скачивались, браузер не запускался. Отдельная одноразовая проверка от 2026-09-29 описана ниже.

Этот раздел дополняет предыдущие наблюдения по точному архиву `@proxyshard/shardx@2.0.3`. Архив был получен пользователем в изолированной VM командой `npm.cmd pack ... --ignore-scripts`; позднее сам SDK был установлен только в отдельный временный каталог с `--ignore-scripts` для фиксации точной версии зависимости.

### Идентичность и состав архива

- SHA-1 (`d614bf8d857b0a6f8d8a3b15812cfe6c1839f631`) и SHA-512 SRI (`sha512-VflpCBOhLijJaC34s62Z1ex8qbRs1I1LTWsNjkV+/nBUtpvMATmlhD1vjKdPMluVSGS5I4XUyklNQ9rI4VB0sQ==`) локального `.tgz` совпали с npm metadata. Опубликованные npm ECDSA-подписи и ключ подписи также проверялись отдельно. Это подтверждает соответствие полученного архива опубликованным метаданным npm, но не происхождение скачиваемых SDK runtime-архивов.
- В `package.json` архива указана зависимость `adm-zip: ^0.5.16`; самого lockfile в опубликованном архиве нет. Точная разрешённая версия `adm-zip` в будущей установке поэтому этим осмотром не установлена.
- Все 11 просмотренных `.js.map` содержат путь исходника вида `../src/*.ts`, но `sourcesContent` пуст. Это означает, что TypeScript-исходники не встроены в карты; само по себе это не признак подмены.

### Подтверждённые наблюдения по коду архива

- `runtime.js`: манифест берётся с изменяемого GitHub `main`, а runtime-файлы скачиваются с отдельного R2-хоста. Нет проверяемой подписи/контрольной суммы архива перед распаковкой, ограничения размера и явного сетевого таймаута. Полученный HTTP `ETag` не сверяется с ожидаемым значением манифеста. Манифест не проходит явную проверку схемы; при ошибке загрузки SDK возвращает пустой манифест.
- Установка/обновление распаковывает данные непосредственно в целевые каталоги. Старый движок удаляется до успешной загрузки нового, поэтому сбой может оставить установку неполной; атомарного переключения и отката не видно. На Windows используется `AdmZip.extractAllTo(..., true)`. Для системного `unzip` допускается код завершения `1`, то есть предупреждения/частичный результат не обязательно прерывают поток.
- `autoResolve.js` при неудаче геолокации через настроенный прокси повторяет запрос напрямую (`geoCheckVia(null)`). Это подтверждённый путь утечки IP сетевого выхода машины провайдеру геолокации, если прокси-вариант завершился ошибкой; после повторной ошибки SDK молча переходит к локальным locale/timezone.
- `deleteProfile(id)` рекурсивно удаляет каталог, собранный через `join(profilesRoot, id)`, а просмотренный путь не показывает валидации `id`. Если вызывающий код может передать недоверенный идентификатор, это создаёт риск удаления за пределами каталога профилей. Не проверялось, какие ограничения накладывает вызывающая сторона SDK.
- Ошибка разбора прокси может включить исходный proxy URL, в том числе credentials. Proxy credentials кодируются для аргумента Chromium, но кодирование не является шифрованием; аргументы передаются в `spawn` и могут быть доступны локальным средствам просмотра процессов. `probeUdp` выполняет SOCKS5-аутентификацию и дополнительную UDP-проверку через фиксированные STUN-адреса.
- При CDP SDK добавляет `--remote-allow-origins=*`; в Chromium это разрешает WebSocket-подключения с любым Origin. Фактическая адресация/доступность CDP в сетевой конфигурации SDK отдельно не проверялась, поэтому внешняя достижимость этим аудитом не доказана. В коде также не видно подтверждения готовности процесса без CDP; таймаут CDP может вернуть сессию без `cdpUrl`, а stop после таймаута посылает принудительное завершение без подтверждения фактического выхода.
- Положительная граница: запуск процесса использует `spawn(binaryPath, argv)` без shell, что снижает риск shell-инъекции. При этом `extraArgs` добавляются как аргументы Chromium и не должны содержать недоверенный ввод.

### Зависимость `adm-zip` и пределы вывода

- В отдельном временном Node-проекте установлен точный локальный `.tgz` командой `npm.cmd install "$ArchivePath" --ignore-scripts --no-audit --no-fund`. Установочные скрипты npm-пакетов были отключены; npm сообщил `added 12 packages in 4s`.
- `npm ls` подтвердил дерево `@proxyshard/shardx@2.0.3` → `adm-zip@0.5.18`. `npm audit --omit=dev` перечислил три advisory — [GHSA-xcpc-8h2w-3j85](https://github.com/advisories/GHSA-xcpc-8h2w-3j85), [GHSA-vwc7-r8mq-g2x9](https://github.com/advisories/GHSA-vwc7-r8mq-g2x9) и [GHSA-7q85-xj36-vmfc](https://github.com/advisories/GHSA-7q85-xj36-vmfc) — сообщил о двух уязвимостях высокой серьёзности и `No fix available`. Значит, проверенная установка SDK действительно разрешает уязвимую версию зависимости; объявленный диапазон `^0.5.16` не позволяет обычным разрешением перейти на `0.6.1`.
- Полный PowerShell transcript (запись команд и вывода) сохранён пользователем на VM в `%TEMP%\shardx-sdk-2.0.3-audit\01-npm-install-check.txt`; файл журнала пока не скопирован в репозиторий.
- На этапе этой проверки 2026-09-28 скачан и установлен только npm SDK с зависимостями. Не скачивались архивы движка или библиотеки отпечатков, не вызывались методы runtime-установки, не запускался браузер и не проводились динамические сетевые тесты. Целостность npm `.tgz` не подтверждает целостность последующих runtime-загрузок.
- Практический вывод не меняется: не использовать SDK с реальными профилями/секретами до закрытия вопросов целостности runtime-архивов, зависимости `adm-zip`, обновления и утечки прямого геозапроса. Разработка v2 с `FakeBrowserRuntime` этим аудитом не блокируется. Это дополнение не является разрешением на установку или запуск ShardX.

## Отдельная одноразовая проверка запуска в VM — 2026-09-29

После статического аудита пользователь отдельно разрешил один smoke-test (краткую проверку запуска) в одноразовой виртуальной машине. Это не возобновляет Phase 0, не принимает SDK для рабочего использования и не разрешает новые загрузки или запуски.

- Архив `@proxyshard/shardx@2.0.3`, полученный через `npm pack`, совпал с метаданными npm по SHA-1 (`d614bf8d857b0a6f8d8a3b15812cfe6c1839f631`) и SHA-512 SRI (контрольная строка целостности: `sha512-VflpCBOhLijJaC34s62Z1ex8qbRs1I1LTWsNjkV+/nBUtpvMATmlhD1vjKdPMluVSGS5I4XUyklNQ9rI4VB0sQ==`). SDK был установлен из этого локального архива в отдельный временный проект с `--ignore-scripts`; установочные скрипты не выполнялись.
- `npm audit --omit=dev` сообщил о двух уязвимостях высокой серьёзности в проверенном дереве зависимостей, включая `adm-zip@0.5.18`, и указал `No fix available`. Три GHSA указаны выше в разделе об этой зависимости.
- При первом использовании SDK инициализировались среда выполнения и библиотека цифровых отпечатков; вывод показал `Fingerprint library: 723845/723845`. Пользователь подтвердил, что видимое окно браузера открылось и работало, затем нажал Enter для остановки. Переходы на сайты, вход в аккаунты, проверка прокси и диагностика отпечатка не выполнялись.
- Для передачи тестового файла с хоста в гостевую Windows через Hyper-V «Интерфейс гостевой службы» временно включали; после передачи его вернули в выключенное состояние (`Enabled: False`) и проверили на хосте. Независимая проверка дерева процессов в госте не состоялась: `Get-CimInstance Win32_Process` вернул WMI `Invalid class`. Скрипт после Enter вызывал `run.stop()` и удаление временного профиля, но завершение всего дерева процессов этим не доказано.
- Статический вывод о загрузчике не изменился: в просмотренном пути не найдено независимой проверки подписи/хеша runtime-архивов перед распаковкой, а манифест берётся с изменяемой ветки `main`. Успешный одиночный запуск доказывает только работоспособность этого сценария, не целостность поставки и не безопасность SDK. D-008 остаётся открытым.
