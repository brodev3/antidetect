> Статус: практический Phase 0 VM-spike закрыт 2026-08-21 через согласованную корректировку scope; наблюдения достаточны для foundation, но supply-chain и live-runtime gates остаются открыты
> Последняя ревизия: 2026-09-22
> Текущая контрольная точка: локальный технический gate Phase 2 пройден 22.09.2026 в текущем рабочем дереве `antidetect-v2-public`. Профильный API/UI slice — сквозной минимальный срез — подключён поверх общего SQLite handle; данные переживают повторное открытие, список поддерживает bounded search/sort с allowlist и Unicode-поиск кириллицы, а постоянный `profileCode` хранится в SQLite и возвращается API. Frozen install, quality loop, 131 тест, production build, startup integration 4/4 и dependency audits проходят локально; формальный Git checkpoint и удалённый CI текущего снимка не подтверждены. Интеграция настоящего ShardX не разрешена.

## Исходное состояние

Legacy — старая версия, отброшенный TypeScript-прототип и пользовательские черновики сохранены только локально. Публичная ветка начинается с чистой основы v2. Решение зафиксировано в [ADR-0005](adr/0005-clean-v2-foundation.md).

До дальнейшей реализации нельзя:

- удалять legacy или discarded prototype;
- наследовать prototype internal APIs, database schema, package boundaries или старые tests;
- переносить prototype code, кроме отдельного небольшого self-contained фрагмента после review по ADR-0005;
- автоматически нормализовать dirty worktree;
- создавать checkpoint/tag/branch без подтверждения;
- повторно загружать или обновлять ShardX, а также менять зависимости, без отдельного согласования.

## Принципы выполнения

- Работать короткими проверяемыми фазами, разбитыми на небольшие reviewable шаги.
- Один шаг по возможности решает одну задачу, раскрывает одну основную учебную тему и заканчивается отдельной проверкой.
- После каждого смыслового diff разбирать результат с пользователем и останавливаться перед следующим изменением.
- Доставлять небольшие сквозные сценарии: интерфейс → API → сохранённый результат. Phase 2 использует тестовые метаданные, Phase 3 — `FakeBrowserRuntime`, тестовую замену движка. Они не требуют новых загрузок ShardX и не доказывают возможности настоящего движка.
- Разделять факты, target и hypotheses.
- Не добавлять инфраструктуру без доказанной необходимости.
- Каждая фаза заканчивается проверками, артефактами и явным gate.
- Следующая фаза не начинается при незакрытом критичном gate.

Единица шага — наблюдаемый результат с проверкой, а не отдельный файл или декоративная правка. До первого сквозного сценария внешний вид текущей страницы фиксируется; исправления читаемости, доступности и ошибок допустимы, новый дизайн не является условием продвижения. Открытое решение блокирует только соответствующую операцию, а не всю независимую разработку. Новое исследование начинается с одного вопроса, критерия завершения и отдельного разрешения на внешние эксперименты.

## Phase 0 — repository audit и ShardX spike

Цели:

- сохранить legacy/prototype неизменными и использовать только согласованное изолированное spike-окружение;
- выполнять ShardX только в одноразовой виртуальной машине Windows x64 без личных данных, общих папок и секретов основной системы;
- маркировать результаты, зависящие от виртуализации, и не переносить их автоматически на физическую Windows;
- проверить актуальные ShardX SDK API, dependencies и terms;
- выполнить минимальный Windows launch;
- проверить persistent profile, proxy, CDP, stop и unexpected exit;
- исследовать crash/restart, process identity и process-tree termination;
- определить возможность reattach;
- проверить engine download, timeout и concurrent first install;
- проверить заявленные fingerprint surfaces black-box методом.

Артефакты:

- заполненный `docs/spikes/phase-0-shardx.md`;
- dependency/licensing evidence;
- подтверждённые runtime limitations;
- принятое recovery решение или явный blocker;
- обновлённые ADR/architecture/decision log.

Exit gate:

- понятно, как spawned browser идентифицируется, отслеживается, останавливается и обрабатывается после падения API;
- proxy fail-closed behavior проверено фактическим external-IP experiment;
- небезопасные предположения удалены;
- принято явное `go`, `scope adjustment` или `no-go`.

До закрытия gate нельзя начинать широкую реализацию v2.

### Scope adjustment от 2026-08-21

Пользователь закрыл практический VM-spike после получения достаточного evidence о lifecycle, process identity, orphan behavior, CDP и proxy failure. Полный исследовательский список не является условием для clean foundation: после отдельного `go` можно начать Phase 1 с `FakeBrowserRuntime` — тестовой заменой реального runtime — и без загрузки/запуска ShardX.

Это не отменяет условия допуска: D-008 остаётся до установки движка, D-005/A-009 — до реальных CDP/прокси-сценариев, D-006 — до адаптера настоящих процессов, D-011/A-012 — до заявлений о поверхностях отпечатка. Модель сохраняемой занятости по ADR-0009/D-014 уже выбрана для SQLite-схемы, а безопасное восстановление и runtime-переходы моделируются в Phase 2–3. Настоящий `ShardXRuntime` не начинается, пока соответствующие решения не приняты отдельно.

## Phase 2 — persistence/domain

Результат для пользователя: создать профиль в UI — интерфейсе — и увидеть ту же запись после перезапуска API. Это первый сквозной сценарий, а не настоящий запуск ShardX.

Последовательность небольших шагов:

1. До записи продуктовых данных базовый guard из ADR-0010/D-015, D-002 baseline и shared SQLite/Kysely boundary уже реализованы: основное SQLite-соединение захватывает эксклюзивную блокировку, Kysely использует его же native handle, а connectivity check выполняется до продуктовых каталогов и HTTP-порта. API принимает только literal loopback с проверенным `Host/Origin`; `ApiRuntime` проверяет порядок, идемпотентность и bounded shutdown штатного закрытия. Локально проверены одинаковые и независимые временные корни, межпроцессное отклонение второго владельца, внешний `API_HOST` до создания root, продолжение работы владельца и повторное получение после завершения первого через `test:integration`. Read-only recovery barrier подключён к startup до `listen()` и проверен отказом с сохранённым run; базовая session boundary из ADR-0014 теперь защищает product API, а process-aware recovery policy, более сильная local authentication, платформенное поведение сигналов и Linux CI остаются открыты. Ограниченная часть D-010 для профилей закрыта ADR-0013; session gate остаётся обязательным перед чувствительными маршрутами. `better-sqlite3@13.0.3` и `kysely@0.29.5` закреплены.
2. [x] Добавить миграции и репозиторий профилей. На 2026-09-21 миграции `schema_migrations`/`profiles`/`profile_code_sequence`, application port `ProfileRepository` и SQLite-адаптер с create/find/list реализованы и проверены на временной базе; `profileCode` выдаётся сервером, хранится отдельно от UUID `id`, backfill — заполнение уже существующих строк — и последовательность переживают повторное открытие root. Повторный запуск миграций идемпотентен, а сценарий обновления предыдущей схемы не теряет профили. Создание и чтение через API и UI реализованы; форма отправляет только `displayName`, а список перечитывается после подтверждённого ответа. Использовать явно тестовую запись identity — идентичности браузера; она не подтверждает готовность настоящего движка.
3. [x] Представление занятости выбрано: отдельная `browser_runs` с блокирующими `starting`, `running`, `stopping`, `recovery_required` и partial unique index зафиксированы в ADR-0012; миграция и проверки настоящей временной SQLite проходят. `BrowserRunRepository`, SQLite-адаптер и lifecycle-сервис подключают transition guard и per-profile mutex к созданию/переходам `browser_runs`; проверены конфликт второго создания записи запуска, повторный переход в `stopped` без изменения результата и конкурентное создание записи одного профиля. Ни настоящие, ни подменные процессы пока не запускаются; это не проверка команды Stop.
4. [x] Реализовать read-only recovery barrier до готовности product API: `BrowserRunRepository.listOccupying()` читает сохранённые active runs, а `BrowserRunRecoveryBarrier` возвращает `ready` только при пустом наборе. Любой `starting`, `running`, `stopping` или `recovery_required`, включая запись без PID/process identity, оставляет результат `blocked`; статусы не меняются. Сценарии terminal history и всех блокирующих статусов покрыты временной SQLite.
5. [x] Подключить read-only barrier к startup до `listen()` и определить безопасный результат для product API при найденных блокирующих runs: API завершается до открытия порта, post-ownership directories не создаются, а durable statuses не меняются. Black-box integration-тест покрывает сохранённый `starting` run.
6. [x] Контракт создания и чтения профилей по D-010, политика Host/Origin по D-002 и базовая session boundary по ADR-0014 приняты в ADR-0013/0014. Реализованы строгие Zod-схемы с `id` и постоянным `profileCode`, application service и NestJS API поверх общего SQLite handle для `POST /profiles`, `GET /profiles/:profileId` и ограниченного `GET /profiles`; список принимает bounded `search`, `sortBy` и `sortOrder` с allowlist. Black-box тесты проверяют реальные `LIMIT/OFFSET`, SQL-фильтр/сортировку, status codes, OpenAPI, Host/Origin, session cookie, выдачу последовательных кодов и сохранение после повторного открытия базы; отдельный SQLite-тест подтверждает регистронезависимый поиск кириллицы. Более сильная local auth, secrets и Start/Stop в этот шаг не входят.
7. [x] Подключить read-only web к `GET /profiles`: общий Zod-контракт валидирует ответ, Vite proxy — локальный прокси разработки — сохраняет localhost `Host/Origin` boundary, а UI показывает loading/error/empty states. `?demo` оставлен явным read-only режимом для визуальной проверки статической таблицы; при отсутствии status/proxy/identity UI использует нейтральные placeholders и `Unknown`, а не выдумывает готовность.
8. [x] Добавить UI-сценарий создания профиля через `POST /profiles`: форма отправляет только `displayName`, блокирует повторную отправку через `isSubmitting`, показывает безопасную ошибку и после подтверждённого ответа перечитывает список через `GET`. API client валидирует request/response общими Zod-схемами; product actions Start/Stop остаются неактивными.

## Phase 3 — lifecycle через fake runtime

Цели:

- определить application-owned `BrowserRuntime`;
- реализовать управляемый `FakeBrowserRuntime`;
- подключить существующие блокировки операций одного профиля к командам движка;
- реализовать start, stop, exit handling и events;
- внедрить launch/stop/timeout/unexpected-exit failures;
- детерминированно проверить concurrency и idempotency.
- подключить Start/Stop и GET состояния к API/UI; до команд закрыть D-004, включая Stop во время запуска и повторные запросы;
- реализовать безопасную модель восстановления занятости и завершения API с подменными процессами по D-014/D-015: конечный статус допускается только после подтверждённого завершения или отказа до создания процесса. Общий метод перехода статусов не является продуктовой командой и не публикуется напрямую через HTTP; Phase 5 не откладывает выбор этих правил;
- после одной законченной функции дать пользователю небольшое самостоятельное изменение или тест, не повышая учебный уровень автоматически.

Exit gate:

- concurrent start одного profile вызывает не более одного launch;
- разные profiles выполняются независимо;
- repeated stop безопасен;
- ошибка после создания процесса либо подтверждённо очищает его, либо сохраняет занятость после перезапуска API; новый Start и удаление отклоняются до подтверждённого освобождения;
- штатное закрытие пользователем и неожиданное завершение различаются; неизвестное состояние не показано как безопасно остановленное;
- команды работают из UI с явно обозначенным тестовым движком; состояние восстанавливается через GET, поток SSE пока не обязателен;
- lifecycle tests не требуют Chromium.

## Phase 5 — reconciliation

Цели:

- инспектировать OS processes при startup;
- защититься от PID reuse;
- сверять все записи занятости, включая потерю управления, и освобождать их только по подтверждённому результату;
- обрабатывать lost handles и spawn crash window;
- находить application-owned orphans, не затрагивая чужой Chromium;
- подтвердить на Windows правила восстановления, уже определённые и проверенные с подменными процессами в Phase 2–3.

Exit gate:

- поведение после перезапуска определено для каждого состояния занятости;
- missing process исправляет stale state;
- reused PID отклоняется;
- live uncontrollable process следует documented safe policy;
- Windows recovery scenarios проверены.

## Acceptance scenarios MVP

Перед завершением MVP проверить:

1. Два concurrent starts одного profile создают не более одного browser.
2. Starts разных profiles не используют global lock.
3. Падение API во время `starting` приводит к documented recovery.
4. External browser termination обновляет state.
5. Запись занятости освобождается только после подтверждения отсутствия принадлежащих запуску процессов.
6. Live process с потерянным handle следует принятой recovery policy.
7. Reused PID не принимается за наш browser.
8. Proxy failure не вызывает silent direct fallback.
9. Proxy password отсутствует в API, SSE, logs, OpenAPI, errors и snapshots.
10. Повторный stop безопасен и идемпотентен.
11. Failure после spawn не оставляет permanent unmanaged orphan.
12. Занятый профиль нельзя удалить, включая запуск, остановку и неразрешённую потерю управления.
13. Concurrent operations сохраняют DB и registry invariants.
14. UI/SSE reconnect восстанавливает истину через GET.
15. Interrupted engine installation не считается healthy installation.
16. Неудачная очистка после создания процесса сохраняет занятость; повторные Start и удаление отклоняются и после перезапуска API.
17. Второй экземпляр API с тем же каноническим корнем получает `APP_ROOT_IN_USE` до миграций, продуктовых каталогов, восстановления и HTTP-порта; владелец продолжает работу, разные тестовые корни независимы, а после штатного или аварийного завершения владельца новый процесс получает корень и выполняет восстановление до готовности.
18. Закрытие окна пользователем, Stop во время запуска и завершение API следуют согласованной модели; неопределённый результат не освобождает профиль.
19. Сбой между изменением SQLite и каталога при удалении восстанавливается; повтор операции безопасен, чужие каталоги не затрагиваются.
20. Созданный через UI профиль переживает перезапуск API; ошибки, пустой список и состояния занятости отражаются без ложного успеха.
21. Обновление подготовленной БД предыдущей версии и восстановление согласованной резервной копии проверены до выпуска.

Каждый сценарий автоматизируется, где это практично. OS/real-engine behavior подтверждается отдельными Windows integration/smoke tests.
