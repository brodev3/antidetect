> Статус: практический Phase 0 VM-spike закрыт 2026-08-21 через согласованную корректировку scope; наблюдения достаточны для foundation, но supply-chain и live-runtime gates остаются открыты
> Последняя ревизия: 2026-10-17
> Текущая контрольная точка: тестовая модель Phase 3 проверена; в Phase 4 ведётся изолированная работа с ShardX. Целевая платформа `Windows`/`macOS`/`Linux` сохраняется в профиле и передаётся генератору; существующую платформу можно менять в интерфейсе только в режиме `?fake-runtime`. Ручной тестовый процесс не доказывает восстановление ShardX или всей группы процессов браузера. D-001/D-006/D-008 остаются открытыми.

## Исходное состояние

Legacy — старая версия, отброшенный TypeScript-прототип и пользовательские черновики сохранены только локально. Публичная ветка начинается с чистой основы v2. Решение зафиксировано в [ADR-0005](adr/0005-clean-v2-foundation.md).

До дальнейшей реализации нельзя:

- удалять legacy или discarded prototype;
- наследовать prototype internal APIs, database schema, package boundaries или старые tests;
- переносить prototype code, кроме отдельного небольшого self-contained фрагмента после review по ADR-0005;
- автоматически нормализовать dirty worktree;
- создавать checkpoint/tag/branch без подтверждения;
- повторно загружать или обновлять ShardX, а также менять зависимости, без отдельного согласования.

## Принципы выполнения

- Работать короткими проверяемыми фазами, разбитыми на небольшие reviewable шаги.
- Один шаг по возможности решает одну задачу, раскрывает одну основную учебную тему и заканчивается отдельной проверкой.
- После каждого смыслового diff разбирать результат с пользователем и останавливаться перед следующим изменением.
- Доставлять небольшие сквозные сценарии: интерфейс → API → сохранённый результат. Phase 2 использует тестовые метаданные, Phase 3 — `FakeBrowserRuntime`, тестовую замену движка. Они не требуют новых загрузок ShardX и не доказывают возможности настоящего движка.
- Разделять факты, target и hypotheses.
- Не добавлять инфраструктуру без доказанной необходимости.
- Каждая фаза заканчивается проверками, артефактами и явным gate.
- Следующая фаза не начинается при незакрытом критичном gate.

Единица шага — наблюдаемый результат с проверкой, а не отдельный файл или декоративная правка. До первого сквозного сценария внешний вид текущей страницы фиксируется; исправления читаемости, доступности и ошибок допустимы, новый дизайн не является условием продвижения. Открытое решение блокирует только соответствующую операцию, а не всю независимую разработку. Новое исследование начинается с одного вопроса, критерия завершения и отдельного разрешения на внешние эксперименты.

## Phase 0 — repository audit и ShardX spike

Цели:

- сохранить legacy/prototype неизменными и использовать только согласованное изолированное spike-окружение;
- выполнять ShardX только в одноразовой виртуальной машине Windows x64 без личных данных, общих папок и секретов основной системы;
- маркировать результаты, зависящие от виртуализации, и не переносить их автоматически на физическую Windows;
- проверить актуальные ShardX SDK API, dependencies и terms;
- выполнить минимальный Windows launch;
- проверить persistent profile, proxy, CDP, stop и unexpected exit;
- исследовать crash/restart, process identity и process-tree termination;
- определить возможность reattach;
- проверить engine download, timeout и concurrent first install;
- проверить заявленные fingerprint surfaces black-box методом.

Артефакты:

- заполненный `docs/spikes/phase-0-shardx.md`;
- dependency/licensing evidence;
- подтверждённые runtime limitations;
- принятое recovery решение или явный blocker;
- обновлённые ADR/architecture/decision log.

Exit gate:

- понятно, как spawned browser идентифицируется, отслеживается, останавливается и обрабатывается после падения API;
- proxy fail-closed behavior проверено фактическим external-IP experiment;
- небезопасные предположения удалены;
- принято явное `go`, `scope adjustment` или `no-go`.

До закрытия gate нельзя начинать широкую реализацию v2.

### Scope adjustment от 2026-08-21

Пользователь закрыл практический VM-spike после получения достаточного evidence о lifecycle, process identity, orphan behavior, CDP и proxy failure. Полный исследовательский список не является условием для clean foundation: после отдельного `go` можно начать Phase 1 с `FakeBrowserRuntime` — тестовой заменой реального runtime — и без загрузки/запуска ShardX.

Это не отменяет условия допуска: D-008 остаётся открытым для установщика и обновления в продукте; его остаточный риск принят только для ограниченной оценки в одноразовой VM. D-005 переоткрыт и принят узко: CDP разрешён только как внутренний канал остановки и восстановления, без внешней автоматизации и раскрытия адреса через API, события, журналы или диагностику. Адрес, переподключение после перезапуска API и подтверждение выхода процесса ещё надо безопасно реализовать и проверить; D-001/D-006 остаются открытыми. A-009 остаётся до реального proxy-сценария, D-011/A-012 — до заявлений о поверхностях отпечатка. Модель сохраняемой занятости по ADR-0009/D-014 уже выбрана для SQLite-схемы, а безопасное восстановление и runtime-переходы моделируются в Phase 2–3. Настоящий `ShardXRuntime` не начинается, пока применимые условия допуска не выполнены.

## Phase 2 — persistence/domain

Результат для пользователя: создать профиль в UI — интерфейсе — и увидеть ту же запись после перезапуска API. Это первый сквозной сценарий, а не настоящий запуск ShardX.

Последовательность небольших шагов:

1. До записи продуктовых данных базовый guard из ADR-0010/D-015, D-002 и общая граница SQLite/Kysely уже реализованы: основное SQLite-соединение захватывает эксклюзивную блокировку, Kysely использует его же native handle, а connectivity check выполняется до продуктовых каталогов и HTTP-порта. API принимает только literal loopback с проверенным `Host/Origin`; `ApiRuntime` проверяет порядок, идемпотентность и bounded shutdown штатного закрытия. Локально проверены одинаковые и независимые временные корни, межпроцессное отклонение второго владельца, внешний `API_HOST` до создания root, продолжение работы владельца и повторное получение после завершения первого через `test:integration`. По решению 2026-09-26 занятость отдельного browser run больше не блокирует готовность всего API: run остаётся занимающим профиль, а будущие команды проверяют его занятость на уровне профиля. Process-aware recovery, платформенное поведение сигналов и Linux CI остаются открыты. Защита от программ на самом компьютере не входит в принятую границу MVP; D-002 реализует Host/Origin/session gate для браузерных запросов. Ограниченная часть D-010 для профилей закрыта ADR-0013; этот gate остаётся обязательным перед чувствительными маршрутами. `better-sqlite3@13.0.3` и `kysely@0.29.5` закреплены.
2. [x] Добавить миграции и репозиторий профилей. На 2026-09-21 миграции `schema_migrations`/`profiles`/`profile_code_sequence`, application port `ProfileRepository` и SQLite-адаптер с create/find/list реализованы и проверены на временной базе; `profileCode` выдаётся сервером, хранится отдельно от UUID `id`, backfill — заполнение уже существующих строк — и последовательность переживают повторное открытие root. Повторный запуск миграций идемпотентен, а сценарий обновления предыдущей схемы не теряет профили. Создание и чтение через API и UI реализованы; форма отправляет только `displayName`, а список перечитывается после подтверждённого ответа. Использовать явно тестовую запись identity — идентичности браузера; она не подтверждает готовность настоящего движка.
3. [x] Представление занятости выбрано: отдельная `browser_runs` с блокирующими `starting`, `running`, `stopping`, `recovery_required` и partial unique index зафиксированы в ADR-0012; миграция и проверки настоящей временной SQLite проходят. `BrowserRunRepository`, SQLite-адаптер и lifecycle-сервис подключают transition guard и per-profile mutex к созданию/переходам `browser_runs`; проверены конфликт второго создания записи запуска, повторный переход в `stopped` без изменения результата и конкурентное создание записи одного профиля. Ни настоящие, ни подменные процессы пока не запускаются; это не проверка команды Stop.
4. [x] Реализовать read-only recovery inspection: `BrowserRunRepository.listOccupying()` читает сохранённые active runs, а `BrowserRunRecoveryBarrier` возвращает снимок `ready`/`blocked` без изменения статусов. Сценарии terminal history и всех блокирующих статусов покрыты временной SQLite; этот результат больше не является глобальным условием готовности API.
5. [x] Первоначальная интеграция barrier блокировала запуск API при любом сохранённом run. Решение 2026-09-26 заменило её: API поднимается, а `recovery_required` остаётся занятым состоянием профиля. Startup integration-тест проверяет открытие `/health` и неизменность записи; глобальные проверки владения корнем и базы остаются.
6. [x] Контракт создания и чтения профилей по D-010, политика Host/Origin по D-002 и базовая session boundary по ADR-0014 приняты в ADR-0013/0014. Реализованы строгие Zod-схемы с `id` и постоянным `profileCode`, application service и NestJS API поверх общего SQLite handle для `POST /profiles`, `GET /profiles/:profileId` и ограниченного `GET /profiles`; список принимает bounded `search`, `sortBy` и `sortOrder` с allowlist. Black-box тесты проверяют реальные `LIMIT/OFFSET`, SQL-фильтр/сортировку, status codes, OpenAPI, Host/Origin, session cookie, выдачу последовательных кодов и сохранение после повторного открытия базы; отдельный SQLite-тест подтверждает регистронезависимый поиск кириллицы. Более сильная local auth, secrets и Start/Stop в этот шаг не входят.
7. [x] Подключить read-only web к `GET /profiles`: общий Zod-контракт валидирует ответ, Vite proxy — локальный прокси разработки — сохраняет localhost `Host/Origin` boundary, а UI показывает loading/error/empty states. `?demo` оставлен явным read-only режимом для визуальной проверки статической таблицы; при отсутствии status/proxy/identity UI использует нейтральные placeholders и `Unknown`, а не выдумывает готовность.
8. [x] Добавить UI-сценарий создания профиля через `POST /profiles`: форма отправляет только `displayName`, блокирует повторную отправку через `isSubmitting`, показывает безопасную ошибку и после подтверждённого ответа перечитывает список через `GET`. API client валидирует request/response общими Zod-схемами; product actions Start/Stop остаются неактивными.
9. Правила восстановления с `FakeBrowserRuntime` — управляемой тестовой заменой браузерного движка — реализуются вместе с контрактом `BrowserRuntime` и командами в Phase 3. Сохранённая занятость блокирует только повторную операцию над тем же профилем, а не готовность всего API. D-001/D-006 и реальная идентичность процессов не закрываются этим переносом.
10. Добавлять прокси, журнал запусков и события только к конкретному сценарию. D-003 закрывается до хранения секретов прокси, D-007 — до сохраняемого журнала событий, D-016 — до удаления профиля с его каталогом. Не создавать все будущие таблицы заранее.

Exit gate:

- создание и чтение профиля работают через API/UI, данные сохраняются после перезапуска;
- два запуска, удерживающих занятость одного профиля, невозможны по ограничению SQLite;
- миграции проверены на новой и предыдущей версии БД; неизвестная версия, несовпадение имени или пропуск в истории отклоняются до новых миграций; ошибка записи истории откатывает таблицу и индекс текущей миграции;
- invalid transitions отклоняются;
- проверки настоящей временной SQLite проходят, включая Windows; реальные пользовательские каталоги не используются.

Локальный результат аудита 22.09.2026: все пункты exit gate подтверждены. Полный набор содержит 22 файла с тестами, 131 тест, production build и 4/4 межпроцессных startup-сценария. Phase 2 считается технически закрытой локально; commit/push и удалённый CI являются следующими операционными checkpoint, а не основанием начинать незаявленную интеграцию ShardX.

## Phase 3 — lifecycle через fake runtime

Цели:

- определить application-owned `BrowserRuntime`;
- реализовать управляемый `FakeBrowserRuntime`;
- подключить существующие блокировки операций одного профиля к командам движка;
- реализовать запуск, остановку и внутренние уведомления о завершении; поток SSE — доставка событий клиентам — относится к Phase 6;
- внедрить launch/stop/timeout/unexpected-exit failures;
- детерминированно проверить concurrency и idempotency.
- подключить Start/Stop и GET состояния к API/UI; до команд закрыть D-004, включая Stop во время запуска и повторные запросы;
- реализовать безопасную модель восстановления занятости и завершения API с подменными процессами по D-014/D-015: конечный статус допускается только после подтверждённого завершения или отказа до создания процесса. Общий метод перехода статусов не является продуктовой командой и не публикуется напрямую через HTTP; Phase 5 не откладывает выбор этих правил;
- после одной законченной функции дать пользователю небольшое самостоятельное изменение или тест, не повышая учебный уровень автоматически.

Текущий шаг: application-owned `BrowserLifecycleService` подключён к отдельному
`BrowserRunsModule` через composition hook — точку сборки зависимостей. По
[ADR-0015](adr/0015-asynchronous-browser-run-commands.md) тестовый API-срез
предоставляет асинхронные `POST /profiles/:profileId/start` и
`POST /profiles/:profileId/stop` с `202`, быстрым `409` для Stop во время запуска
и `GET /profiles/:profileId/run` с последним запуском. Fastify `inject()`
проверяет HTTP-коды, повторные команды и безопасную форму ответа без
PID/process identity; lifecycle-тесты проверяют тайм-ауты и поздние результаты.
Тесты жизненного цикла дополнительно моделируют восстановление на подменном
runtime — тестовом исполнителе — после его пересоздания: переподключение разрешено
только при совпадении сохранённых `runId` и `profileId` (идентификаторов запуска
и профиля), серверного `profileDirectory` (каталога данных профиля), PID и `processIdentity` (идентичности процесса). Неизвестный процесс
остаётся занимающим профиль, автоматическая остановка не вызывается. Для уже
`recovery_required` точное совпадение восстанавливает listener (подписку на выход
процесса), переводит запись в `running` и очищает устаревший `failureCode`.
Неизвестная идентичность, таймаут и ошибка поиска сохраняют `recovery_required`.
Это пока не подключено к обычному
`main` и не доказывает поиск процессов в ОС. API больше не блокируется глобально
из-за такого run, но process-aware recovery до открытия обычного API и профильные
команды ещё не связаны в production composition. Black-box API-тесты с
`FakeBrowserRuntime` подтверждают, что успешное переподключение видно как
`running`, повторный Start того же профиля получает `409`, а запуск другого
профиля разрешён; при неизвестном процессе блокируется только его профиль.
`FakeBrowserRuntime` не становится
реальным runtime; выбор production runtime, подключение восстановления при старте,
production wiring (связывание модулей в обычном `main`) и аварийное завершение
остаются отдельными шагами. Граница браузерных запросов D-002 принята и реализована по ADR-0016; проверка произвольных локальных программ средствами ОС не входит в MVP. Для тестового API-среза
уже проверено штатное закрытие: живой браузер не останавливается, незавершённые
`starting`/`stopping` после ограниченного ожидания остаются занятыми как
`recovery_required`, поздний ответ не перезаписывает их состояние.

Уточнения финального аудита от 02.10.2026: подтверждённое завершение имеет единое правило, незавершённые операции учитываются до фактического результата, сохранённый `stopping` без текущей задачи проходит проверку через `recovery_required`, а медленный ответ движка не продлевает срок его ожидания при закрытии API. Уже начатую запись результата в БД служба ожидает до освобождения ресурсов; ошибка или превышение внешнего срока не выдаются за успешное закрытие. Подписка обновляется после точного переподключения; устаревшая ошибка очистки снимается только после успешного сохранения `running`. Подробные правила — в [ADR-0015](adr/0015-asynchronous-browser-run-commands.md).

Exit gate — условия завершения фазы:

- concurrent start одного profile вызывает не более одного launch;
- разные profiles выполняются независимо;
- repeated stop безопасен;
- ошибка после создания процесса либо подтверждённо очищает его, либо сохраняет занятость после перезапуска API; новый Start отклоняется до подтверждённого освобождения; запрет удаления занятого профиля проверяется вместе с реализацией удаления в Phase 6;
- штатное закрытие тестового API не останавливает `running` браузер; подтверждённый процесс можно переподключить, а незавершённые Start/Stop безопасно сохраняют занятость;
- штатное закрытие пользователем и неожиданное завершение различаются; неизвестное состояние не показано как безопасно остановленное;
- команды работают из UI с явно обозначенным тестовым движком; состояние восстанавливается через GET, поток SSE пока не обязателен;
- lifecycle tests не требуют Chromium.

Для ручной проверки UI добавлена отдельная команда `corepack pnpm run dev:fake-api` и режим `http://127.0.0.1:5173/?fake-runtime`. Они используют только данные в памяти и явно показывают, что настоящий браузер не запускается. FakeBrowserRuntime намеренно остаётся в отдельном тестовом запуске: обычный `main.ts` не должен подключать тестовую подмену; production runtime wiring относится к Phase 4.

Проверка 27.09.2026 после SQLite-сценариев восстановления: `format:check`,
`lint`, `typecheck`, `test` (210 тестов), production `build` и
`test:integration` (4/4 межпроцессных сценария) проходят. Временная SQLite-БД
подтверждает, что `unknown` (состояние процесса неизвестно) и таймаут сохраняют
занятость профиля, а `absent` (исполнитель подтвердил отсутствие процесса)
переводит запуск в `failed` и освобождает профиль. Это проверяет сохранение и
правила переходов, но не обнаружение или идентификацию реального процесса ОС.
Ручной сценарий переключения отпечатка, Start/Stop и конфликта занятого профиля
прошёл через изолированную тестовую API-композицию. 27.09 после запуска тестового профиля
перезагрузка страницы восстановила `Running` повторным запросом `GET`; остановка вернула
`Ready`. API-процесс при этой проверке оставался запущен, поэтому она не проверяет
перезапуск API или восстановление реального процесса. Штатная команда `dev:fake-api`
пересобрала API, но не смогла занять порт `3000` (`EADDRINUSE`); существующий процесс
не останавливался.

Уточнение границ Phase 3 от 27.09.2026: обычный `main.ts` намеренно не подключает
FakeBrowserRuntime; связь жизненного цикла с основной точкой входа появится вместе
с реальным адаптером в Phase 4. Безопасное удаление профиля и полноценное управление
прокси отнесены к Phase 6; блокировка удаления занятого профиля проверяется вместе
с этой операцией. В Phase 4 требуется проверить минимальную передачу настроек
прокси и отказ без перехода на прямое соединение: настроенный, но неработающий
прокси не должен приводить к запуску напрямую. До передачи реальных учётных данных
прокси необходимо решить, как безопасно хранить их на Windows. Локальный технический gate
Phase 3 пройден; это не является доказательством работы ShardX или процессов ОС.

Финальный аудит и локальные проверки Phase 3 закрыты 02.10.2026: `corepack pnpm run format:check`, `corepack pnpm run lint`, `corepack pnpm run typecheck`, `corepack pnpm test` (27 файлов, 290 тестов), `corepack pnpm run build`, `corepack pnpm run test:integration` (4/4) и `git diff --check` прошли. Учебный уровень отдельно не повышен.

## Phase 4 — ShardX adapter

Условия D-001/D-006 по идентичности и восстановлению реального процесса остаются обязательными критериями приёмки, но не блокируют изолированную реализацию и тестирование адаптера. До их прохождения нельзя подключать runtime к обычному `main`, автоматически завершать неоднозначные процессы или освобождать их занятость. D-005 принят узко: видимый ручной запуск с `cdp: true` только для внутренних команд остановки и восстановления; адрес не выходит за пределы адаптера, внешняя автоматизация отложена. В VM уже подтверждено подключение отдельного Node.js-процесса к ранее сохранённому адресу и штатное закрытие выбранного дерева Chromium, но автоматическое обнаружение адреса после перезапуска API, авторизация и проверка полного жизненного цикла не доказаны. SDK 2.0.3 добавлял `--remote-allow-origins=*`; принятый остаточный риск ограничен однопользовательским MVP без сетевой экспозиции и требует отсутствия утечки адреса. D-008 принят только для оценки SDK в одноразовой VM; установщик и обновление в продукте остаются вне принятого решения. Статические факты и ограничения аудита описаны в [заметке SDK 2.0.3](spikes/shardx-sdk-2.0.3-static-audit.md). Принятая модель занятости и команды Phase 2–3 сохраняются. Любые новые загрузки и запуски требуют отдельного разрешения; закрытый Phase 0 не повторяется целиком.

Цели:

- реализовать изолированный `ShardXRuntime`;
- добавить controlled engine status/installation;
- сопоставить application profiles с ShardX inputs;
- [x] передавать в fingerprint generator выбранную целевую платформу профиля (`Windows`, `macOS` или `Linux`), не смешивая её с Windows x64 платформой хоста;
- [x] проверять соответствие сгенерированной identity запрошенной платформе и покрывать поддерживаемые варианты фикстурами без загрузки или запуска движка;
- [x] изменить платформу уже созданного профиля через lifecycle-команду: при включённом отпечатке атомарно сохранить платформу и новую identity, при выключенном — сохранить платформу без генерации и отсоединить старую identity; проверить блокировку и занятость. Селектор UI, API-клиент и fake generator проверяют этот сценарий в `?fake-runtime`; обычный `main.ts` маршрут пока не подключает;
- проверить минимальную передачу настроек прокси и убедиться, что при его отказе запуск не переходит на прямое соединение; реальные учётные данные прокси не подключать до принятия безопасной политики их хранения на Windows;
- зарегистрировать handles и exit listeners;
- выполнить redaction runtime data;
- пройти реальный Windows smoke flow.

Exit gate:

- application создаёт, запускает, сохраняет и останавливает реальный ShardX profile;
- изолированный адаптер принимает выбранную платформу отпечатка и отклоняет несовместимый результат генерации до сохранения профиля;
- настроенный прокси не имеет скрытого перехода на прямое соединение при отказе;
- unexpected exit наблюдается;
- после перезапуска API recovery находит только единственный процесс-кандидат с точным путём ShardX executable, точным `profileDirectory`/`userDataDir` и временем создания не раньше сохранённого `runCreatedAt`; если PID/`processIdentity` уже сохранены, они также должны совпасть, а CDP listener должен принадлежать проверенному дереву;
- неполная проверка, несколько кандидатов или несовпадение признаков дают `unknown`/`recovery_required`; `absent` разрешён только после полной проверки, а остановка освобождает занятость лишь после подтверждения ОС, что всё принадлежащее запуску дерево завершилось; чужой Chromium не затрагивается;
- secrets отсутствуют в diagnostics;
- smoke procedure повторяема.

- Windows recovery scenarios проверены.

## Acceptance scenarios MVP

Перед завершением MVP проверить:

1. Два concurrent starts одного profile создают не более одного browser.
2. Starts разных profiles не используют global lock.
3. Падение API во время `starting` приводит к documented recovery.
4. External browser termination обновляет state.
5. Запись занятости освобождается только после подтверждения отсутствия принадлежащих запуску процессов.
6. Live process с потерянным handle следует принятой recovery policy.
7. Reused PID не принимается за наш browser.
8. Proxy failure не вызывает silent direct fallback.
9. Proxy password отсутствует в API, SSE, logs, OpenAPI, errors и snapshots.
10. Повторный stop безопасен и идемпотентен.
11. Failure после spawn не оставляет permanent unmanaged orphan.
12. Занятый профиль нельзя удалить, включая запуск, остановку и неразрешённую потерю управления.
13. Concurrent operations сохраняют DB и registry invariants.
14. UI/SSE reconnect восстанавливает истину через GET.
15. Interrupted engine installation не считается healthy installation.
16. Неудачная очистка после создания процесса сохраняет занятость; повторные Start и удаление отклоняются и после перезапуска API.
17. Второй экземпляр API с тем же каноническим корнем получает `APP_ROOT_IN_USE` до миграций, продуктовых каталогов, восстановления и HTTP-порта; владелец продолжает работу, разные тестовые корни независимы, а после штатного или аварийного завершения владельца новый процесс получает корень и выполняет восстановление до готовности.
18. Закрытие окна пользователем, Stop во время запуска и завершение API следуют согласованной модели; неопределённый результат не освобождает профиль.
19. Сбой между изменением SQLite и каталога при удалении восстанавливается; повтор операции безопасен, чужие каталоги не затрагиваются.
20. Созданный через UI профиль переживает перезапуск API; ошибки, пустой список и состояния занятости отражаются без ложного успеха.
21. Обновление подготовленной БД предыдущей версии и восстановление согласованной резервной копии проверены до выпуска.

Каждый сценарий автоматизируется, где это практично. OS/real-engine behavior подтверждается отдельными Windows integration/smoke tests.
