> Статус: активный

> Авторитетен для: незакрытых решений, непроверенных гипотез и active risks

## Правила

1. Нет evidence — нет статуса `Проверено`.
2. Существенное принятое решение оформляется ADR; здесь остаётся строка и ссылка.
3. Предположение становится фактом только со ссылкой на audit, test или spike report.
4. Риск закрывается только после проверки mitigation.
5. Vendor claims и старые version snapshots не считаются текущими фактами.
6. Детальные Phase 0 результаты хранятся в `docs/spikes/phase-0-shardx.md`.

21.08.2026 практический VM-spike закрыт через согласованную корректировку scope. Открытые решения, предположения и риски ниже не считаются принятыми: они перенесены в gates соответствующих фаз и не разрешают live ShardX integration.

#### D-001: план проверки управления процессом после потери `ChildProcess` (2026-09-27)

Это план проверки, а не выбранная реализация и не разрешение запускать ShardX. `ChildProcess` — объект Node.js для исходного дочернего процесса. Подменные тесты Phase 3 проверяют только контракт приложения и не подтверждают состояние процесса Windows.

**Этап A — проверка механизма Windows без ShardX; обязательна до настоящего адаптера.** Использовать одноразовый вспомогательный процесс, созданный локальной проверкой, с тестовым каталогом профиля; при необходимости добавить дочерний процесс для проверки дерева процессов.

1. Запустить вспомогательный процесс, сохранить маркер `runId` (идентификатор запуска) и сведения для проверки личности: PID (числовой идентификатор процесса), время создания процесса, канонический путь к исполняемому файлу и каталог профиля.
2. Завершить только процесс-контроллер, оставив вспомогательный процесс работать. После перезапуска контроллер должен найти и переподключиться ровно к одному кандидату, только если совпали все сохранённые признаки. Один `runId` или PID сам по себе не доказывает личность процесса.
3. Проверить отрицательные случаи и различать результаты поиска:
   - Полный ограниченный поиск доказал отсутствие связанного процесса и незавершённого запуска: вернуть `absent` (подтверждённо отсутствует), перевести запуск в `failed` и освободить профиль.
   - Поиск неполный или неоднозначный: маркер потерян, признаки личности не совпали, PID уже принадлежит другому процессу, кандидатов несколько или ОС отказала в доступе. Не подключаться и не останавливать кандидатов; сохранить `recovery_required` и занятость.
4. Разделить повторное получение дескриптора проверенного процесса и команду его остановки. Успех остановки засчитывается только после подтверждённого ОС завершения, а не после принятия команды; таймаут или отсутствие подтверждения оставляет профиль занятым. Если способ управляет деревом процессов, проверить завершение всех принадлежащих тесту процессов и сохранность отдельного постороннего процесса.
5. Зафиксировать воспроизводимые команды и результаты, версию Windows, PID и время создания одноразовых процессов, а также итоговые состояния запусков. Не использовать пользовательские профили и секреты.

Первая ручная пробная проверка ограничена положительным сценарием с одноразовым помощником: сценарий находится в `apps/api/tests/windows.process.recovery.smoke.ps1` и запускается командой `powershell -NoProfile -File .\apps\api\tests\windows.process.recovery.smoke.ps1`. `runId` задаёт имя локального системного события (одноразового сигнала между процессами), а первый контроллер сохраняет PID, время создания, путь исполняемого файла и каталог тестового профиля. Второй контроллер повторно получает объект процесса по PID и сверяет время создания, путь программы и маркер профиля; затем открывает событие, отправляет кооперативный сигнал и ждёт подтверждённого завершения процесса и маркера подтверждения. Это проверяет повторное получение контроля по сохранённой личности процесса, но не поиск нескольких кандидатов, состояния «подтверждённо отсутствует»/«неизвестно», принадлежность дочерних процессов или дерево браузера; проверка не подтверждает будущий механизм обнаружения процессов в приложении.

Способ остановки пока не выбран. Документация Node.js указывает, что `ChildProcess.kill('SIGTERM')` на Windows завершает процесс принудительно и резко; Microsoft описывает `TerminateProcess` как безусловное завершение, которое само по себе не завершает дочерние процессы. Поэтому ни один из этих вызовов нельзя называть штатным закрытием браузера. Этап A может проверить обнаружение, сверку личности и наблюдение за выходом безопасного вспомогательного процесса; проверку принудительной остановки не выполнять до отдельного решения. См. [Node.js Child process](https://nodejs.org/api/child_process.html#subprocesskillsignal), [Microsoft `TerminateProcess`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess) и [Terminating a Process](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process).

Успех этапа A подтвердит только выбранный механизм повторного получения контроля над тестовым процессом Windows. Он не доказывает поведение Chromium или ShardX. Проверку реального браузера выполнять отдельным этапом после отдельного разрешения пользователя и прохождения gates установки и целостности движка; она должна дополнительно подтвердить завершение всего принадлежащего браузеру дерева и сохранность постороннего Chromium. Ни документальный план, ни fake-тест не закрывают D-001.

#### D-014: настройки fingerprint (отпечатка браузера) (2026-09-26)

По умолчанию при создании профилю назначается автоматически сгенерированный
поддерживаемый отпечаток; пользователь может создать профиль в режиме «Без
отпечатка». Оба режима допустимы для запуска. Отключение сохраняет назначенную
идентичность, повторное включение использует её же; смена назначает новую
неизменяемую идентичность. Изменение режима и назначения разрешено только при
отсутствии блокирующего запуска и использует ту же `ProfileOperationMutex`
(блокировку операций одного профиля), что и Start (команда запуска), чтобы не
соревноваться с запуском. Отсутствие прокси означает прямое соединение.

Это принятое продуктовое поведение, но контракт программного интерфейса, схема
хранения и интерфейс пользователя ещё не реализуют его. Фактический запуск без
отпечатка должен быть подтверждён на среде выполнения ShardX; D-014 остаётся
открытым для изменения прокси и других параметров запуска.

#### D-015: частичная политика штатного закрытия API (2026-09-26)

Для тестового API-среза `BrowserRunsModule` штатное закрытие не останавливает
`running` браузеры, ожидает фоновые Start/Stop до 5 секунд и сохраняет оставшиеся
`starting`/`stopping` как `recovery_required`; поздние ответы после дедлайна
игнорируются. Это проверено только с `FakeBrowserRuntime`. Обычный `main` пока не
подключает модуль управления браузером, аварийное завершение без обработчика
жизненного цикла, проверка идентичности процесса и интеграция с настоящим runtime остаются открытыми;
полный D-015 не закрыт.

### D-004: команды Phase 3 (2026-09-23)

Статус: решение принято в [ADR-0015](adr/0015-asynchronous-browser-run-commands.md) и реализовано для тестового API-среза. D-002 принят и реализован для браузерных запросов по ADR-0016. Подключение настоящего адаптера к обычному `main` требует проверок D-001/D-006 и незакрытой части D-015; установка и обновление в продукте требуют D-008. Прежний синхронный HTTP-срез ждал завершения `start()` и `stop()`, а GET читал только блокирующий запуск.

Асинхронный контракт: `202 Accepted` означает, что команда принята и запись запуска сохранена, но не утверждает, что браузер уже запущен или остановлен. UI читает итог через `GET` — запрос состояния. Один профиль по-прежнему защищён mutex и частичным уникальным индексом SQLite.

| Ситуация | Ответ | Правило |
| --- | --- | --- |
| Start без блокирующего запуска | `202`, `{ run: starting }` | Создать новый run и одну отслеживаемую задачу запуска. |
| Повторный Start при `starting`, `running`, `stopping` или `recovery_required` | `409 ACTIVE_BROWSER_RUN_CONFLICT` | Не создавать второй run и не вызывать движок повторно; клиент читает существующий run через GET. |
| Stop во время `starting` | `409 BROWSER_RUN_START_IN_PROGRESS` | Быстро отказать без постановки Stop в очередь. После перехода в `running` клиент может повторить команду. |
| Stop при `running` или повторно при `stopping` с незавершённой задачей | `202`, `{ run: stopping }` | Перевести run в `stopping` до ответа и выполнить не более одного вызова движка. Пока задача учитывается службой, повторный запрос получает тот же run. |
| Stop при сохранённом `stopping` без незавершённой задачи | `409 BROWSER_RUNTIME_RECOVERY_REQUIRED` | Сохранить `recovery_required` с `RUNTIME_STOP_INTERRUPTED`, не повторять остановку до проверки процесса. Уточнение аудита от 02.10.2026: [ADR-0015](adr/0015-asynchronous-browser-run-commands.md). |
| Stop после конечного состояния либо до первого запуска | `200`, `{ run: latest }` или `{ run: null }` | Не вызывать движок снова. |
| Stop при `recovery_required` | `409 BROWSER_RUNTIME_RECOVERY_REQUIRED` | Не завершать процесс по одному PID и не освобождать профиль без проверки. |
| GET состояния | `200`, `{ run: latest }` или `{ run: null }` | Возвращать последний созданный run, включая `failed` и `stopped`, чтобы UI восстанавливался после перезагрузки. |

Ожидание HTTP ограничено сохранением записи и постановкой задачи; вызовы движка имеют отдельные сроки ожидания. Истечение срока, потеря ответа или поздний результат не должны забывать возможный процесс: задача продолжает отслеживать позднее завершение и сохраняет `recovery_required`, пока отсутствие принадлежащего ей процесса не подтверждено. Простое прекращение ожидания Promise без продолжения обработки результата не подходит.

Альтернатива — сохранить синхронные ответы `200` после полного запуска/остановки. Она требует держать HTTP-запрос открытым во время работы движка и отдельно решать зависший Start, Stop в очереди и потерянный ответ клиента. Выбранный контракт согласуется с отображением `Starting`/`Stopping` в UI, состояний запуска и остановки. Учёт фоновых задач и ограниченное ожидание при штатном закрытии проверены с тестовой заменой движка по ADR-0015; восстановление настоящих процессов и незакрытые части D-015 остаются отдельными условиями. Более сильная проверка локальных программ средствами ОС не входит в принятую границу D-002 для MVP.

Проверено для тестового среза: коды HTTP, повторные команды, Stop во время задержанного Start, сроки ожидания и поздние результаты движка, GET конечного состояния, отказ новым командам и проверкам восстановления при закрытии API, а также сохранение занятости и восстановление после повторного открытия SQLite-БД. Медленная проверка восстановления перестаёт удерживать блокировку на дедлайне закрытия; её поздний результат не применяется. Эти тесты с `FakeBrowserRuntime`, тестовой заменой движка, не доказывают поведение ShardX или дерева процессов Windows и не закрывают весь D-015.

### Исторический checkpoint recovery barrier (2026-09-19)

Read-only `BrowserRunRecoveryBarrier` и `BrowserRunRepository.listOccupying()` проверены на временной SQLite: terminal history не блокирует готовность, а любой `starting`, `running`, `stopping` или `recovery_required`, включая запись без PID/process identity, возвращает `blocked` без изменения данных. Startup integration-тест подтверждает отказ до `listen()` и отсутствие post-ownership directories. Это снижает риск ошибочного освобождения профиля, но не закрывает process-aware reconciliation или управление живым процессом.

26.09.2026 принято уточнение: активный или неразрешённый запуск одного профиля больше не является причиной останавливать весь API. Запись и уникальное ограничение SQLite сохраняют занятость этого профиля; API может обслуживать остальные доступные операции. Это не выполняет process-aware reconciliation: переподключение и маршруты управления браузером пока не подключены к обычному `main`.

Исторические ADR-0001/0002 имеют статус `Superseded` и не определяют текущую v2 architecture.

### Дополнительное наблюдение для D-005/D-006 — 01.10.2026

В одноразовой VM проверочный скрипт только для чтения автоматически обнаружил единственный адрес CDP на loopback (локальном сетевом интерфейсе) среди открытых портов `chrome.exe` и подтвердил PID (идентификатор процесса) владельца, путь к исполняемому файлу и время создания процесса. Это частичное свидетельство возможности обнаружения, а не восстановление после перезапуска API. Скрипт не связал процесс с точным `userDataDir` (каталогом данных профиля) и `runId` (идентификатором запуска), не проверил выход launcher (процесса запуска) и не сравнил время процесса с записью запуска; команда по WebSocket (протоколу двунаправленного соединения) не выполнялась. Поэтому D-005/D-006 остаются открытыми до проверки идентичности процесса и восстановления в реальном адаптере. Подробности и ограничения зафиксированы в [дополнении к VM-spike](spikes/phase-0-shardx.md).

### Дополнительная проверка идентичности процесса Windows для D-006 — 01.10.2026

В виртуальной машине тестовый сценарий повторно открыл временный PowerShell-процесс (процесс командной оболочки Windows) по PID (идентификатору процесса), времени создания и пути к исполняемому файлу, проверил маркер тестового профиля и получил подтверждение штатного завершения без принудительного завершения процесса. Это не проверка ShardX/`chrome.exe`, сбоя между созданием процесса и записью в SQLite (встроенную базу данных) или восстановления API; D-006 остаётся открытым. Подробности: [результат теста Windows](spikes/phase-0-shardx.md).

### Проверка активной группы ShardX для D-006 — 01.10.2026

Read-only (только для чтения) зонд обнаружил семь `chrome.exe` с одним SDK `userDataDir` (каталогом данных профиля) и ожидаемым путём ShardX Chromium; результат `PASS_SHARDX_PROFILE_PROCESS_ASSOCIATION`. Родительский PID `4036` был `node.exe`, но он не был подтверждён как конкретный smoke-launcher (процесс запуска теста). Связь с `runId` приложения и recovery после перезапуска API не проверены, поэтому D-006 остаётся открытым. Полные данные: [результаты ShardX-зонда](spikes/phase-0-shardx.md).

### Проверка владельца CDP-порта в дереве ShardX-процессов — 02.10.2026

Пользователь запустил обновлённый зонд только для чтения в одноразовой VM при работающем браузере. Он прочитал файл `DevToolsActivePort` (метаданные подключения Chromium), сопоставил указанный там порт с TCP-listener-ом Windows (открытым сетевым портом) и проверил PID владельца по полному дереву из семи ShardX-процессов. Результат: `PASS_SHARDX_PROFILE_AND_CDP_OWNER_ASSOCIATION`, код `0`; владелец — PID `4444`. В проверенном снимке listener был только на loopback (локальном сетевом интерфейсе). Адрес, порт и WebSocket-путь не печатались; HTTP/WebSocket-запросы, команды браузеру и изменения процессов не выполнялись.

Это частичное runtime-evidence для связи CDP-порта с деревом одного профиля. Оно не связывает процесс с записью запуска API/`runId`, не сравнивает время создания процесса со временем запуска, не проверяет поиск после перезапуска API и не подтверждает остановку браузера. Родительский `node.exe` по-прежнему не подтверждён как конкретный smoke-launcher. D-005/D-006 не закрыты. Подробности: [результаты ShardX-зонда](spikes/phase-0-shardx.md).

### Проверка после закрытия Chromium — 02.10.2026

После закрытия браузера повторный снимок read-only зонда показал ноль `chrome.exe` и ноль процессов с SDK-каталогом профиля; результат `NO_MATCHING_SHARDX_PROFILE_PROCESS`, exit code `2`. Это ожидаемый код для пустого совпадения, не сбой скрипта. В рамках зонда процессы не останавливались.

Наблюдение подтверждает, что в момент проверки Chromium не оставил видимых `chrome.exe` в системе. Оно не проверяет завершение smoke-launcher-а/`node.exe`, запись запуска API, `runId` или восстановление после перезапуска. D-006 остаётся открытым.

### Проверка повторного открытия и ожидания Windows-процесса — 09.10.2026

В одноразовой VM пользователь выполнил `apps/api/tests/windows.process.recovery.smoke.ps1`. Второй контроллер повторно открыл тестовый процесс и сверил PID (идентификатор процесса), время создания, путь исполняемого файла и маркер каталога профиля. Затем он передал сигнал с уникальным для тестового запуска именем, дождался подтверждённого выхода вспомогательного процесса и проверил его запись-подтверждение. Принудительное завершение не применялось.

Это проверяет механизм ожидания повторно открытого Windows-процесса на тестовом помощнике, но не ShardX/Chromium, запись `browser_run` в SQLite, восстановление настоящего `runId`, всё дерево браузера или интеграцию `BrowserRuntime.recover`. Поэтому D-006 остаётся открытым; обычный `main.ts` не должен подключать реальный адаптер только на основании этого smoke-теста. Скрипт и границы проверки описаны в [current-state.md](current-state.md).
